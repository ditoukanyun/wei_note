# 演示操作手册

## 一、在公司电脑上启动

需要 Docker Desktop，或 Docker Engine + Docker Compose v2。建议为 Docker 分配至少 4 GB 内存。首次构建需要访问 Docker 镜像仓库和 Maven Central，不需要在宿主机安装 Java、Maven 或 Python。

将整个分享目录复制到公司电脑，在其中的 `案例` 目录打开终端，执行：

```bash
docker compose up -d --build
```

镜像构建阶段会执行 7 项 Java 测试。等待依赖就绪和配置初始化完成后，三个应用实例会启动。

| 页面 | 默认地址 | 用途 |
| --- | --- | --- |
| 中文演示台 | http://localhost:8081/ | 主演示入口，聚合三个实例的状态 |
| 开发实例乙 | http://localhost:8082/api/runtime | 单独核对配置与启动标识 |
| 测试观察实例 | http://localhost:8083/api/runtime | 验证环境隔离，不注册任务 |
| Nacos 原生控制台 | http://localhost:8848/nacos/ | 定位并修改真实配置 |

服务仅将上述端口映射到本机回环地址。本地教学环境关闭 Nacos 鉴权，数据库凭据是示例值；若移植到共享环境，需要接入该环境已有的访问控制。

查看启动情况：

```bash
docker compose ps -a
docker compose logs --tail 100 app-a app-b
docker compose logs --tail 50 config-init
```

`config-init` 显示 `Exited (0)` 是正常结果。Nacos、ZooKeeper 和 PostgreSQL 应处于 healthy；应用刚显示 running 时可能仍在初始化，等演示台显示三个实例。

## 二、会前完整彩排

执行真实环境自动验证：

```bash
docker compose run --rm verify
```

它会重置本案例开发数据和开发、测试配置，依次验证动态刷新、两个实例分片、失败补偿、额外重跑、非法配置、环境隔离以及批量限制。成功后打印“全部端到端验证通过”，并恢复演示起点。

验证使用 Python 容器，宿主机不需要 Python。验证失败时保留现场，结合应用日志排查。

## 三、现场顺序与讲述提示

### 步骤 1：重置并记录初始状态

在演示台点击“重置演示数据与配置”，等待三张实例卡片刷新。

| 对象 | 预期 |
| --- | --- |
| 开发实例甲、乙 | 关闭，批量 100 |
| 测试观察实例 | 关闭，批量 7 |
| 订单 | 12 笔待补偿 |
| 业务流水 | 0 |
| 模拟故障 | 已开启，针对订单 1005 |

指出启动标识、启动时间与配置版本的位置。容器里的 Java PID 通常都是 1，所以 PID 只能辅助观察，主要比较启动标识与启动时间。

台词：“这两个开发实例读取同一配置空间，测试实例读取另一配置空间。接下来发布一次配置，观察三个实例的区别。”

### 步骤 2：发布开发配置，不重启刷新

在配置区选择开发环境，勾选开启补偿，批量填 20，点击“发布到 Nacos”。

等待开发实例甲、乙都显示开启、20；测试实例仍是关闭、7。比较启动标识，确认未发生重启。

台词：“接口读到的已经是业务将采用的新快照。两个实例刷新有传播时间，演示中等它们一致后再触发任务。”

### 步骤 3：展示 Nacos 原生控制台

打开 Nacos 页面，依次定位：

1. 命名空间选择“开发环境”，标识为 `share-dev`。
2. 配置管理中找到 Group 为 `ORDER_SERVICE`、Data ID 为 `order-service.yaml` 的配置。
3. 展示 `enabled: true` 和 `batch-size: 20`。
4. 切换“测试环境”，相同 Group / Data ID 下应是 `false / 7`。

可选演示：直接在原生控制台把开发批量改为 10，点击发布，回演示台观察刷新，然后改回 20。

### 步骤 4：第一次触发，观察分片与单笔失败

讲解时先类比“两个标签页各有自己的轮询定时器”，引出两个服务实例需要协调；再用前端按区域 `filter` 的思路解释业务分片范围。详见 [[前端定时器与ElasticJob类比讲解]]。

回到演示台，确认两个开发实例均已开启，批量为 20。点击一次“触发任务”，等待“运行分片”为 0。

展示实际分片分配与执行记录：三个分片由两个实例分担，分片 0、1、2 分别处理华东、华南、华北。具体哪个实例拿到哪个分片，以现场结果为准。

框架分片状态 `PENDING` 表示当前未执行、等待调度；业务订单是否已补偿，要查看订单状态和本案例的执行记录。

预期结果：

| 指标 | 结果 |
| --- | --- |
| 成功订单 | 11 |
| 待补偿订单 | 1，即 1005 |
| 业务流水 | 11 |
| 1005 最近错误 | 模拟下游超时 |
| 本轮分片记录 | 3 条，其中一个分片含业务失败 |

台词：“每个分片都只查自己的区域，1005 的失败不会阻止本例继续处理同批其他订单；处理结束后再向框架汇报该分片存在失败。”

### 步骤 5：恢复依赖，再次触发补偿

点击“恢复模拟依赖”，再点击一次“触发任务”。

预期：12 笔全部成功、流水为 12；1005 的尝试次数为 2，其他订单仍为 1。查看新一轮三个分片的记录，其中只有 1005 对应分片产生一笔新增成功。

台词：“我们再次执行了任务，业务查询依靠待补偿状态选中这笔订单。控制台没有自动还原上次失败输入。”

可以补一句：“就像页面上的重新执行按钮，再次进入处理路径，具体处理哪些数据仍由业务参数与状态决定。”

### 步骤 6：额外触发，验证不会重复写入

再触发一次，业务流水仍为 12，订单尝试次数保持原值。

台词：“已成功订单不会再次被扫描；即使同一订单并发进入处理，事务内的状态复查、行锁和业务唯一约束也提供了防护。并发路径还有自动测试覆盖。”

### 步骤 7：结束时展示两份材料

打开 [[配置命名规则]] 与 [[定时任务代码模板]]。说明会后可以按模板新增一个自己的任务。

## 四、备用命令

以下命令在 macOS / Linux 的终端执行；Windows PowerShell 使用 `curl.exe` 替代 `curl`。默认端口如果已修改，请同步替换。

发布开发配置：

```bash
curl -X POST http://localhost:8081/api/config/dev -H 'Content-Type: application/json' -d '{"enabled":true,"batchSize":20}'
```

查询实际运行值与启动标识：

```bash
curl http://localhost:8081/api/runtime
curl http://localhost:8082/api/runtime
curl http://localhost:8083/api/runtime
```

触发、恢复故障、查询结果：

```bash
curl -X POST http://localhost:8081/api/jobs/trigger -H 'Content-Type: application/json' -d '{}'
curl -X POST http://localhost:8081/api/demo/failure -H 'Content-Type: application/json' -d '{"enabled":false}'
curl http://localhost:8081/api/summary
curl http://localhost:8081/api/orders
curl http://localhost:8081/api/runs
curl http://localhost:8081/api/shards
```

只重置订单、不改 Nacos 配置：

```bash
curl -X POST http://localhost:8081/api/demo/reset -H 'Content-Type: application/json' -d '{}'
```

## 五、可选加演

### 批量限制确实影响处理数量

重置后恢复依赖，发布开发配置 `true / 2`。触发一次，三个分片各最多处理两笔，共产生 6 条流水；第二次触发后达到 12 条。这样可以直接看到批量配置如何影响业务。

### 非法配置保留上次有效值

在 Nacos 原生控制台把开发批量改成 0。演示台显示拒绝原因，业务仍使用上次有效快照。再改回 20，错误状态消失。教学页面会在发布前校验，因此这个演示需要通过 Nacos 原生页面修改。

### 观察单实例承担全部分片

在无分片运行时暂停开发实例乙：

```bash
docker compose stop app-b
```

等待注册中心感知，再触发任务，观察剩余实例接管三个分片的分配。恢复：

```bash
docker compose start app-b
```

该实验展示后续调度时的重新分配。示例未开启 failover，不把它当成“正在运行分片立即故障转移”的演示。

## 六、常见问题

| 现象 | 检查顺序 |
| --- | --- |
| Docker 连接失败 | 先启动 Docker Desktop，再运行 `docker info` |
| 拉取镜像或依赖超时 | 使用公司允许的代理或镜像仓库配置，提前下载；不要在分享现场首次构建 |
| 端口占用 | 复制 `.env.example` 为 `.env`，改外部端口后重新启动 |
| `config-init` 非零退出 | 查看该服务日志，确认 Nacos healthy，再运行 `docker compose up -d config-init` |
| 配置没变 | 核对 Namespace / Group / Data ID，确认已发布，查看实例卡片是否拒绝变更 |
| 触发后没有处理订单 | 检查开关、待补偿状态、任务日志，等上一轮结束后再触发 |
| 两个实例配置短暂不同 | 等待回调传播完成；持续不一致时检查客户端连接和拒绝原因 |
| 修改 schema 后数据库没变 | 初始化脚本只在新数据卷上运行；按下一节的重建步骤初始化本案例 |

## 七、停止与重新开始

保留数据，停止本案例：

```bash
docker compose down
```

后续再次启动会保留数据卷与 Nacos 配置。初始化服务只创建缺失配置，重新彩排可点击页面上的重置按钮。

需要完全清空本案例的数据卷时：

```bash
docker compose down -v
docker compose up -d --build
```

`down -v` 会删除本 Compose 项目的演示数据与配置；执行前确认当前目录和项目确为本案例。

## 八、公司网络不能联网时

在与公司电脑相同 CPU 架构的可联网环境中完成构建和彩排，再导出运行所需镜像：

```bash
docker image save -o java-share-images.tar java-share-demo:1.0.0 nacos/nacos-server:v2.5.1 zookeeper:3.9.3 postgres:16.6-alpine python:3.12-alpine
```

将镜像文件和整个分享目录一起复制到公司电脑：

```bash
docker image load -i java-share-images.tar
docker compose up -d --no-build --pull never
```

离线运行不需要构建镜像。Apple 芯片 Mac 通常是 arm64，公司 Windows / Linux 通常是 amd64；导出的镜像必须匹配目标架构。源码包支持在目标电脑本地重新构建；本次附带的源码压缩包不包含体积较大的镜像文件。
