## 一、先确定怎么讲

### 1. 分享主线

**一项订单补偿任务，如何做到运行参数可调整、多实例能协作、失败后可恢复？**

用同一业务案例贯穿两个小节：

- **4.1 配置中心**：控制补偿开关、每批处理数量，不重启应用即可生效；开发和测试环境互不影响。
- **4.3 ElasticJob**：定时扫描待补偿订单，按区域分片交给多个实例执行；模拟失败后，在控制台手动触发补偿。

保留原课程编号，本次聚焦 4.1 和 4.3，搜索模块另行展开。

### 2. 讲解方法

每节统一采用“**业务问题 → 最小概念 → 关键代码 → 现场演示 → 使用边界**”的顺序。

- 听众已有 Java 基础，直接进入 Spring Boot 使用方式，注解与依赖注入只在需要时解释。
- `.env`、feature flag、`node-schedule` 作为一句话类比，帮助理解用途。
- Apollo / Nacos 选团队实际使用的一种做主演示，另一种用一张表对照；团队技术栈未明确前，演示暂按 Nacos 设计。
- 安装中间件、下载依赖提前完成，现场只展示与本次任务有关的配置和代码。
- 源码机制、选型对比和复杂故障演练放入附录。

### 3. 听完应该能做什么

1. 添加一个动态配置，发布后用接口和日志确认业务值已刷新、应用没有重启。
2. 找到应用使用的配置集，解释环境隔离维度。
3. 编写一个最小 `SimpleJob`，读懂分片编号、分片参数和公共参数。
4. 在两个实例上观察分片分配，完成一次手动触发和失败订单补偿。
5. 解释为什么重跑需要幂等，以及故障转移、错过触发和业务异常分别怎么处理。

## 三、4.1 配置中心 Apollo / Nacos 用法（10 分钟）

### 4.1.1 从业务需求切入（1 分钟）

开场可以这样说：

> “补偿任务每批处理 100 笔订单，现在下游压力变大，需要临时改成 20 笔。能不能直接调整，让应用下一轮就使用新值？”

由此引出三个问题：配置放在哪里、谁来发布、应用如何使用新值。

### 4.1.2 先讲配置如何定位与隔离（2 分钟）

| 问题 | Apollo 对应概念 | Nacos 对应概念 |
| --- | --- | --- |
| 属于哪个应用或业务 | AppId，配合 Namespace 组织配置 | 按约定使用 Group、Data ID 组织配置 |
| 当前使用哪个环境 | Environment，配合对应环境服务地址 | Namespace 可用于区分开发、测试、生产环境 |
| 读取哪份配置 | Namespace，必要时结合 Cluster | Namespace + Group + Data ID |

这是一张帮助理解的对照表，两者的 Namespace 含义与层级不同，不能直接一一替换。概念依据：[Apollo Java 客户端指南](https://github.com/apolloconfig/apollo/blob/master/docs/en/client/java-sdk-user-guide.md)、[Nacos 配置模型](https://www.nacos.io/docs/ebook/szf3gh/)。

演示约定：Nacos 使用开发、测试两个 Namespace，Group 为 `ORDER_SERVICE`，Data ID 为 `order-service.yaml`。应用启动时显式指定目标 Namespace 的标识；只切换 Spring Profile，还要确认最终指向的配置空间。

### 4.1.3 讲清“发布后为什么能生效”（2 分钟）

只讲一条链路：**控制台发布 → 客户端接收变更 → Spring 配置或配置对象更新 → 业务读取新值**。

重点展示项目采用的配置加载方式与刷新方式：

- Nacos 的配置加载、刷新开关及 `@RefreshScope` / 配置绑定行为，要与项目的 Spring Boot、Spring Cloud Alibaba 版本对应。
- Apollo 对支持的 Spring 占位符注入提供自动更新；`@ConfigurationProperties` 的自动更新还需要相应刷新处理，不能套用同一结论。
- 启动时复制到普通字段、初始化资源时只读取一次的值，需要额外刷新逻辑。
- 任务每轮开始时读取一份经校验的配置快照，运行中的这一轮保持稳定，新配置用于后续轮次。

依据：[Spring Cloud Alibaba Nacos 接入指南](https://sca.aliyun.com/en/docs/2025.x/user-guide/nacos/quick-start/)、[Apollo 配置注入与更新说明](https://github.com/apolloconfig/apollo/blob/master/docs/en/client/java-sdk-user-guide.md#322-use-of-spring-placeholder)。新旧版本加载方式存在差异，后续代码按团队版本编写。

### 4.1.4 现场演示：加配置 → 动态刷新 → 验证隔离（4 分钟）

准备两个配置项：

| 配置项 | 初始值 | 用途 |
| --- | --- | --- |
| `order.compensation.enabled` | `false` | 是否执行订单补偿 |
| `order.compensation.batch-size` | `100` | 每个分片每批最多处理多少笔订单 |

演示步骤及预期结果：

1. 展示控制台配置位置、客户端连接信息和配置绑定类，说明“加一个配置”涉及哪几处。
2. 请求演示查询接口，展示开关、批量大小、实例标识及启动时间。
3. 将开发环境配置改为 `true` / `20` 并发布。
4. 再请求接口，看到配置值变化、实例标识和启动时间保持一致；展示配置变更日志。
5. 对比测试环境：相同配置项仍保持原值。若时间紧张，提前准备对照截图。

### 4.1.5 用三个边界收尾（1 分钟）

- **适合动态调整**：业务开关、批量大小、业务阈值；端口、已初始化连接池等要看组件是否支持重建。
- **输入需要校验**：例如批量大小限定在合理范围；默认值、非法值和回滚处理写入规范。
- **开关有生效时机**：本案例在每轮开始读取，关闭开关后后续轮次跳过；正在执行的一轮不会因此自动中断。

衔接下一节：“现在我们可以控制任务怎么跑，接下来解决任务由谁跑、数据怎么分。”

## 四、4.3 定时任务 ElasticJob 用法（13 分钟）

### 4.3.1 从单机定时任务走向多实例（1 分钟）

引导问题：“同一个 `@Scheduled` 或 `node-schedule` 任务部署两份，为什么同一批订单可能被处理两遍？”

解释单进程定时器只负责本进程的触发；本案例使用 ElasticJob 协调多个实例的分片分配。演示中采用 ZooKeeper 作为注册中心。

把“多实例只跑一份”说准确：**分片数为 1 时，正常调度下由一个实例执行该分片；分片数大于 1 时，各实例分担不同分片。故障恢复与重跑仍要求业务幂等。** 依据：[ElasticJob 弹性调度](https://shardingsphere.apache.org/elasticjob/current/en/features/elastic/)。

### 4.3.2 写一个最小 Job（2 分钟）

只展示三个位置：

1. **Job 类**：实现 `SimpleJob`，入口为 `execute(ShardingContext context)`。
2. **任务注册配置**：注册中心、`jobName`、Cron、总分片数及分片参数。
3. **业务 Service**：读取配置快照，按分片范围查询待补偿订单，执行处理并记录结果。

任务代码结构讲解顺序：**读取配置 → 判断开关 → 解析分片范围 → 分批查询 → 幂等处理 → 记录成功和失败**。

强调 Job 负责调度适配，业务处理集中到 Service，便于手动补偿时复用。接口依据：[ElasticJob 作业开发](https://shardingsphere.apache.org/elasticjob/current/en/user-manual/usage/job-api/job-interface/)。

### 4.3.3 重点讲分片参数怎么用（3 分钟）

| 概念 | 示例 | 业务代码如何使用 |
| --- | --- | --- |
| `shardingTotalCount` | `3` | 总共划分 3 个逻辑工作单元 |
| `shardingItem` | `0`、`1`、`2` | 当前执行的分片编号，从 0 开始 |
| `shardingItemParameters` | `0=华东,1=华南,2=华北` | 将每个分片映射到一个区域 |
| `context.getShardingParameter()` | 当前分片对应的区域 | 用作查询条件，只扫描该区域订单 |
| `jobParameter` | 约定的公共模式或业务日期 | 各分片共用，字符串内容由业务自行解析 |

依据：[ElasticJob 配置说明](https://shardingsphere.apache.org/elasticjob/current/en/user-manual/configuration/)。

必须讲清楚：

- 分片数与实例数不同：3 个分片可分配给 2 个实例，一个实例可能执行多个分片。
- ElasticJob 分配分片编号，**业务代码负责按编号或参数筛选数据**；如果查询仍然扫全表，就可能重复处理。
- 同一任务的实例需要连接同一个注册中心命名空间、使用一致的任务名和配置，才能参与同一组协调。

按区域划分便于演示参数含义，但实际数据可能倾斜；按订单 ID 取模等策略作为附录，正文采用一种清楚的规则。

### 4.3.4 现场演示：两个实例、三个分片、一次失败补偿（5 分钟）

准备：两个应用实例连接同一演示数据库；12 笔待补偿订单分布在三个区域。日志包含实例、任务名、分片号、区域、订单号和结果。

1. **展示注册与分片**：启动两个实例，在控制台查看实例状态与分片分配。
2. **触发执行**：在团队所用控制台执行一次任务，观察两个实例分担三个区域；展示配置快照中的开关与批量大小。
3. **模拟一笔失败**：受控模拟某笔订单的下游调用失败，保留失败记录和待补偿状态；其余订单正常完成。
4. **恢复并再次触发**：恢复模拟依赖，再在控制台触发任务，业务查询只选待补偿数据。
5. **核对结果**：失败订单被补偿，已完成订单没有重复产生业务效果。

> [!important] 演示前确认触发入口
> 手动触发是再次执行任务，历史失败记录不会因此自动成为输入。本案例依靠“待补偿状态”选择数据。官方 `JobOperateAPI.trigger(jobName)` 提供触发能力；控制台是否暴露入口、是否支持临时参数或历史重跑，应以团队版本和内部封装为准，提前走通。依据：[操作 API](https://shardingsphere.apache.org/elasticjob/current/en/user-manual/usage/operation-api/)、[控制台说明](https://shardingsphere.apache.org/elasticjob/current/en/user-manual/operation/web-console/)。

故障演示期间拉长自动触发间隔，避免下一轮调度提前处理失败订单；提前确认开关已开启。

### 4.3.5 失败了怎么处理（2 分钟）

| 情况 | 处理方向 | 需要避免的误解 |
| --- | --- | --- |
| 业务异常，例如下游超时 | 记录失败数据；采用有次数限制的重试或修复后补偿 | 配置错误处理器不等于业务会自动重试成功 |
| 执行实例宕机 | 按配置使用 failover 接管未完成分片，或后续调度重新分配 | failover 不负责重试所有业务异常 |
| 上一轮太久，错过触发 | 按需求使用 misfire 补偿错过的触发 | misfire 不等于失败订单重试 |
| 手动重跑或故障恢复带来重复处理 | 以业务唯一键、条件更新、事务等机制实现幂等 | 日志显示成功或单纯“先查状态”不足以证明幂等 |

机制依据：[故障转移](https://shardingsphere.apache.org/elasticjob/current/en/features/failover/)、[错过执行](https://shardingsphere.apache.org/elasticjob/current/en/features/misfire/)、[错误处理策略](https://shardingsphere.apache.org/elasticjob/current/en/user-manual/configuration/built-in-strategy/error-handler/)。

用一句话收尾：“调度框架安排执行，业务代码保证重复执行时结果仍然正确。”

## 五、最后沉淀什么（3 分钟）

### 1. 配置命名规则草案

以下为建议的团队约定，后续与现有规范合并：

- 业务配置采用 `业务域.功能.属性`，例如 `order.compensation.batch-size`；多词属性使用小写连字符。
- 布尔开关使用正向语义，如 `enabled`；涉及时间和容量时写明单位，如 `timeout-ms`。
- 环境通过平台隔离维度表达，同一业务配置保持相同名称。
- 每项配置说明用途、类型、默认值、取值范围、负责人、生效时机，以及是否支持动态刷新。
- 发布后验证业务实际读取值；回滚也需要确认各实例已生效。

### 2. 定时任务代码模板应包含的内容

| 模板组成 | 应承担的职责 |
| --- | --- |
| 任务注册配置 | 任务名、Cron、时区、分片数、分片参数和框架策略 |
| Job 入口 | 读取配置快照、判断开关、提取执行上下文、调用 Service |
| 业务 Service | 分片查询、分批处理、幂等控制、失败数据记录与补偿 |
| 执行日志 | 任务名、本次执行标识、实例、分片、业务键、耗时及结果 |
| 操作说明 | 如何查看状态、手动触发、定位失败、确认补偿结果 |

这里先确定模板结构，具体依赖、注解和代码在确认团队版本后补齐。
