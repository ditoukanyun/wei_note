# 配置命名规则

> [!note] 适用范围
> 这是一份可与团队现有规范合并的建议，示例使用订单补偿业务。平台本身的固定属性名遵循平台定义。

## 1. 业务配置项

采用 `业务域.功能.属性`，多词属性使用小写连字符。

| 示例 | 含义 | 说明 |
| --- | --- | --- |
| `order.compensation.enabled` | 是否开启订单补偿 | 正向语义，避免双重否定 |
| `order.compensation.batch-size` | 每个分片每批最多处理数量 | 明确“每分片每批”，避免误认为全局并发量 |
| `order.compensation.timeout-ms` | 补偿调用超时 | 预留示例，单位毫秒；当前案例未实现此项 |
| `order.compensation.max-retries` | 最大重试次数 | 预留示例，当前案例不执行自动重试 |

避免 `flag1`、`config2`、`timeout` 等无法判断业务范围或单位的命名。配置开关应记录负责人和清理条件，已结束的临时开关及时移除。

## 2. 配置集与环境

本案例约定：

| 维度 | 约定 |
| --- | --- |
| Nacos Namespace | `share-dev`、`share-test`，对应开发与测试 |
| Nacos Group | `ORDER_SERVICE` |
| Nacos Data ID | `order-service.yaml` |
| 业务配置项名称 | 各环境相同，值可不同 |

这套约定把环境放在 Namespace 维度，不再把 `dev` / `test` 重复写进每个业务配置项。Data ID 是显式选择的，不依赖特定 Spring Cloud 版本的自动文件名推导。

Apollo 接入时单独记录 AppId、Environment、Cluster、Namespace。两种产品的 Namespace 不能按名称直接等同。

## 3. 每个配置项需要的说明

| 项目 | `batch-size` 示例 |
| --- | --- |
| 完整名称 | `order.compensation.batch-size` |
| 用途 | 每个分片一次调用最多查询的待补偿订单数 |
| 类型与范围 | 整数，1～1000 |
| 初始值 | 开发 100，测试 7 |
| 动态刷新 | 支持 |
| 生效时机 | 下一次分片调用读取快照时 |
| 非法值处理 | 拒绝新配置，保留上次有效快照，记录错误 |
| 关联项 | `order.compensation.enabled` |
| 负责人 | 实际项目填写负责团队与人员 |
| 回滚 | 发布上次有效配置，再确认所有目标实例已采用 |

案例启动时配置缺失或无效会启动失败，便于及时暴露环境问题；运行中收到坏配置会保留上次有效快照。不要把这两种时机的处理方式混为一谈。

## 4. 发布与验证

1. 确认目标环境与配置集，检查类型、范围和单位。
2. 发布完整配置，并观察拒绝日志或告警。
3. 检查各实例实际读取的版本和字段值，不能只看控制台已保存。
4. 触发一批可观察业务，确认批量、开关等行为与新值一致。
5. 需要回滚时重新发布上一版，并重复验证。

本例两个字段作为一个配置集发布，单个实例会原子替换快照；多个实例不提供跨进程的原子切换。若业务需要严格同步生效，还需要版本协调或指定生效时间等方案。

## 5. 本地连接配置与动态业务配置

Compose 的环境变量负责服务地址、命名空间和外部端口；订单补偿开关与批量大小由 Nacos 管理。启动环境变量的变化通常需要重建相应容器，Nacos 业务配置则走运行时监听刷新。
