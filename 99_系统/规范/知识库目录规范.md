# 知识库目录规范

本文是 `40_知识库` 的正式目录规范，也是唯一完整规则来源。`40_知识库/知识库目录规范.md` 只作为入口摘要，避免两份规范长期分叉。

## 规范目标

- 让新增知识先有稳定位置，再开始写内容。
- 让领域入口、专题索引、原子概念、实践清单和资源附件各司其职。
- 先约束新增内容，旧内容按使用频率逐步整理，不做一次性大迁移。
- 让待补知识点有清晰清单，后续可以持续补齐。

## 核心原则

- **规则单源**：完整规则只维护在本文。
- **新增优先**：新建笔记优先遵守规范，旧笔记遇到时再顺手整理。
- **先连接再扩写**：新增知识点时优先补 `area`、`tags` 和相关 wikilink。
- **少搬动，多收敛**：重复概念优先用链接、别名和 MOC 收敛，不急于批量移动。
- **目录服务检索**：目录层级用于帮助定位，不替代 MOC 和双链。

## 目录职责

### 领域目录

领域目录承载一个长期稳定的知识域，例如：

- `40_知识库/后端开发`
- `40_知识库/前端开发`
- `40_知识库/AI`
- `40_知识库/通用技能`
- `40_知识库/交易`
- `40_知识库/DevOps`

领域目录适合放领域 MOC、少量核心入口和稳定专题目录。不要把大量零散概念长期堆在领域根目录。

### 专题目录

专题目录承载一个领域下的稳定主题，例如：

- `40_知识库/后端开发/消息队列`
- `40_知识库/后端开发/系统设计`
- `40_知识库/前端开发/React`
- `40_知识库/AI/AI相关/RAG技术`

专题目录适合放专题 MOC、专题内原子概念、实践流程、检查清单和附件目录。

### MOC

MOC 是知识地图和导航入口，不是普通文章。它负责回答：

- 这个领域或专题包含哪些关键概念。
- 新手或复习时应该按什么路径阅读。
- 它和其他领域有什么连接。
- 哪些知识点需要补齐或更新。

大领域至少应有一个 MOC。专题中文件超过约 20 篇时，也应补一个专题 MOC。

### 原子概念

原子概念只解释一个稳定概念、机制或方法，例如：

- `幂等性.md`
- `OAuth2 与 OIDC 核心概念.md`
- `缓存穿透.md`
- `TypeScript 类型设计.md`

原子概念应优先写清楚定义、要点、示例、相关概念和参考资料。

### 实践清单

实践清单面向执行和复盘，例如：

- 部署检查清单
- 交易复盘模板
- Code Review 清单
- 故障排查流程

实践清单可以放在对应领域或专题目录中。它和原子概念不同，重点是步骤、判断条件和可执行检查项。

### 资源附件

图片、截图、外部资料索引和课程资源不直接堆在领域根目录。优先放在对应专题内：

- 已有 `img` 或 `images` 时沿用既有目录。
- 新建附件目录时优先使用 `资源` 或 `images`，保持同一专题内一致。
- 通用书籍、视频、链接资源可以放到 `50_资源`，知识笔记只保留摘要和链接。

### 迁移内容

从外部导入或历史迁移来的内容，先保留原结构，后续按价值逐步整理：

- 有长期价值的内容，补 frontmatter、MOC 链接和相关概念。
- 临时材料或纯资料，迁移到 `50_资源` 或归档。
- 重复内容，保留主笔记，其他笔记添加指向主笔记的说明。

## 命名规则

- 领域目录使用稳定中文名，例如 `后端开发`、`前端开发`、`通用技能`。
- 专题目录按技术、能力或问题域命名，例如 `消息队列`、`认证授权`、`前端性能`。
- 原子概念使用清晰中文概念名，必要时保留英文缩写，例如 `OAuth2 与 OIDC 核心概念.md`。
- MOC 文件名应包含 `MOC`，例如 `后端开发 MOC.md`、`MOC-Python编程.md`。
- 实践清单文件名应体现使用场景，例如 `ETF-T0-交易检查清单.md`。
- 避免同一概念出现多个近似文件名；需要并存时，在 MOC 中明确主入口。

## MOC 规则

领域 MOC 建议包含：

- 领域目标和能力结构。
- 核心专题列表。
- 推荐学习路径。
- 和其他领域的连接。
- 常用实践入口。
- 最近需要补齐或更新的知识点。

专题 MOC 建议包含：

- 专题定义和适用场景。
- 基础概念。
- 进阶主题。
- 常见问题或实践流程。
- 相关领域链接。

## frontmatter 规则

知识库笔记沿用 `[[99_系统/模板/Wiki_Template|Wiki_Template]]` 的基础结构：

```yaml
---
area:
tags: []
created: YYYY-MM-DD
---
```

使用约定：

- `area` 填领域 wikilink，例如 `[[后端开发]]`、`[[AI]]`、`[[通用技能]]`。
- `tags` 用于补充类型或主题，例如 `moc`、`系统设计`、`检查清单`、`安全`。
- `created` 使用 `YYYY-MM-DD`。
- frontmatter 结束行 `---` 后直接接正文标题，不留空行。
- 新建 MOC 时在 `tags` 中加入 `moc`。

## 新增知识判断流程

新增笔记前，按顺序判断：

1. **是不是项目推进内容？** 是则放入 `20_项目` 或对应项目记录，不放知识库。
2. **是不是外部资料或链接合集？** 是则优先放入 `50_资源`，知识库只保留消化后的摘要和链接。
3. **是不是单一概念？** 是则放入对应领域或专题目录，作为原子概念。
4. **是不是一组概念的导航？** 是则创建或更新 MOC。
5. **是不是执行流程或检查表？** 是则作为实践清单放在对应专题目录。
6. **是不是跨多个领域？** 先选择主要领域落位，再用 wikilink 连接其他领域。

## 渐进整理规则

- 旧内容不因为不合规而立即移动。
- 修改旧笔记时，顺手补 `area`、`tags`、`created` 和相关 wikilink。
- 发现重复概念时，选一个主笔记，其余笔记加“主入口见……”说明。
- 某领域或专题文件超过约 20 篇且没有 MOC，优先补 MOC。
- 附件散落时，优先整理到当前专题的附件目录，不跨领域搬动。
- 目录变更前先确认是否会破坏大量已有 wikilink。

## 维护检查清单

新增或整理知识时检查：

- [ ] 这条内容属于知识库，而不是项目、日记或资源收藏。
- [ ] 文件放在了合适的领域或专题目录。
- [ ] frontmatter 包含 `area`、`tags`、`created`。
- [ ] frontmatter 后没有多余空行。
- [ ] 至少连接了一个相关 MOC 或相关概念。
- [ ] 如果是资源材料，已经判断是否更适合放入 `50_资源`。
- [ ] 如果是重复概念，已经明确主入口。
