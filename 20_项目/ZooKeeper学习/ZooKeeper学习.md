# ZooKeeper 学习

## 背景与目标

用一个小而完整的 Spring Boot 工程把 ZooKeeper 跑起来，目标不是「会调 API」，而是能解释清楚三个问题：

- 为什么 `create` 不会覆盖、改数据必须用 `setData`？
- 为什么 watch 是一次性的，重注册还要换线程？
- 为什么临时顺序节点能当分布式锁，而且崩溃会自动释放？

## 核心结论

| 问题 | 结论 |
| --- | --- |
| 它是什么 | 分布式协调服务，存少量、关键、需要强一致的元数据，不是数据库 |
| 为什么有序 | 所有写请求由 Leader 分配全局递增 zxid，过半确认后提交 |
| 读为什么可能旧 | 读由各节点本地响应，不经过 Leader；要最新值先 `sync` |
| create 为什么不覆盖 | 插入语义，已存在直接 `NODEEXISTS`；改数据用 `setData` |
| 并发控制靠什么 | 每个 znode 的 `version`，`withVersion` 即 CAS |
| watch 为什么一次性 | 服务端不为客户端维护长期订阅；触发后必须重注册 |
| 锁为什么用临时顺序节点 | 临时保证崩溃自动释放，顺序保证公平，监听前驱避免惊群 |
| 锁最大的坑 | 持锁者 GC 停顿超过会话超时 → 出现两个持锁者，需 fencing token |

## 验证

- 文档内 **99 处 `文件:行号` 引用**，已用脚本逐条校验，全部指向真实存在的行。
- 锁实验实测（8 线程 × 5 任务，初始库存 100）：

| 模式 | 期望库存 | 实际库存 | 丢失更新 | 耗时 |
| --- | --- | --- | --- | --- |
| 不加锁 | 60 | 95 | 35 | 199ms |
| 加锁 | 60 | 60 | 0 | 1629ms |

绝对数字随机器浮动，结论稳定：无锁必丢、加锁不丢。
