# ElasticJob 扩展实验与实践

这篇是 [[ElasticJob分享讲稿]] 的独立扩展。优先讲 750 笔订单的分批实验，约 8 分钟；耗时超过间隔、历史窗口补跑放在附录按需选讲。原主体仍为 37 分钟，加入实验后为 45 分钟，另留 5 分钟问答。

## 一、把 12 笔变成 750 笔，会暴露什么

原案例总共 12 笔，每个区域只有 4 笔，默认每片批量 100，一轮很容易覆盖全量。数据增加后，“一次调度结束”与“全部业务数据处理完成”会明显分开。

扩展场景：两个实例、三个区域，每个区域 250 笔，总共 750 笔；每次分片调用最多查询 100 笔，模拟故障关闭。这里继续使用 `SimpleJob`，没有自动循环清空积压，也没有改成 `DataflowJob`。

## 二、8 分钟操作流程

### 1. 会前构建并准备（不计入现场时间）

在本篇 `案例/` 目录执行：

```bash
docker compose up -d --build
docker compose run --rm verify
docker compose run --rm verify-large
```

`verify` 验证基础失败补偿；`verify-large` 验证 750 笔数据的三轮处理、第四轮幂等，以及恢复 12 笔基础场景。两条验证命令依次执行，不要并发运行，都会重置教学数据。

### 2. 载入数据并先预测（约 2 分钟）

打开 [任务演示台](http://localhost:8091/)，确认没有运行中的分片，点击“载入 750 笔扩展数据”。该操作替换本案例的订单、流水与执行记录，自动关闭模拟故障；新订单号从 100001 开始。

确认两个实例的“每分片批量”为 100，汇总显示 750 待补偿、0 成功、0 流水。订单表只展示前 60 笔，汇总指标覆盖全量，避免现场渲染大量表格。

先问：“三个分片、两个实例、每片 100，第一轮最多处理多少？”答案是 **300 笔**。不是两实例乘 100，也不是一次调度就把 750 笔全部处理完。

### 3. 逐轮触发和核对（约 3 分钟）

每轮点击一次“触发一次任务”，等待本轮三条分片记录完成、运行分片回到 0，再进行下一轮。

| 阶段 | 累计成功 | 待补偿 | 累计流水 | 每个区域累计成功 |
| --- | --- | --- | --- | --- |
| 载入后 | 0 | 750 | 0 | 0 |
| 第一轮 | 300 | 450 | 300 | 100 |
| 第二轮 | 600 | 150 | 600 | 200 |
| 第三轮 | 750 | 0 | 750 | 250 |
| 第四轮 | 750 | 0 | 750 | 250 |

第四轮仍产生新的分片调用记录，但不会新增业务流水。全部订单的尝试次数为 1。若设置了其他本地批量，结果会不同；表格对应本案例默认的每片 100。

备用命令：

```bash
curl -X POST http://localhost:8091/api/demo/large -H 'Content-Type: application/json' -d '{}'
curl -X POST http://localhost:8091/api/jobs/trigger -H 'Content-Type: application/json' -d '{}'
curl http://localhost:8091/api/summary
```

Windows PowerShell 使用 `curl.exe`。每轮触发都走真实 ElasticJob 操作 API，演示台没有直接调用业务处理器。

### 4. 走读取数点，再恢复基础场景（约 3 分钟）

打开 `CompensationService.java`：

```sql
SELECT order_id FROM compensation_order
WHERE region = ? AND status = 'PENDING'
ORDER BY order_id
LIMIT ?;
```

本例一次分片调用只查询一次。当前批次处理成功后，状态离开 `PENDING`，所以下一轮按同样查询自然选到下一批。这里没有增加 `OFFSET`。

再看 `DemoDataService.java`：`seedLarge()` 生成三个区域各 250 笔；`reset()` 重新建立原来的 12 笔，并恢复针对 1005 的故障注入。两个数据切换入口都拒绝在检测到运行分片时执行；这属于教学入口保护，不能代替生产环境的调度暂停与并发治理。

最后点击“重置演示订单”，确认回到 12 待补偿、0 流水。不要把扩展数据留给下一次基础分享。

### 可直接讲的话术

> 刚才 12 笔数据让一轮执行看起来像处理完了全部订单。现在数据变多，同样的 Job 一轮只处理三个批次，总共最多三百笔。框架这一轮已经结束，业务还有四百五十笔积压，这两个事实并不矛盾。容量规划既要看任务有没有报错，也要看积压有没有持续下降。

## 三、从这个实验继续追问

### 1. 前端分页类比：为什么不能随便加 OFFSET

假设按待处理状态查询，第一批 100 笔成功后已离开结果集。下一次若使用 `OFFSET 100`，可能跳过当前结果集最前面的 100 笔，造成漏处理。

本例每轮从待补偿集合起点重新取数，因为成功状态会推进。更大规模或复杂查询可以设计基于唯一排序键的游标、数据领取或时间窗口；失败重试的查询路径也要一起设计，不能让被游标越过的失败数据永久遗漏。

### 2. 能不能让一轮不断取，直到处理完

可以作为下一阶段方案，但必须定义结束条件、最大时长、数据边界和失败策略，避免新数据持续到达时一直不退出。

ElasticJob 的 `DataflowJob` 将 `fetchData` 与 `processData` 分开。流式模式会持续获取，直到返回空集合或 null；处理后没有正确推进业务状态，可能反复取到同一批数据。当前案例没有启用该模式。[官方作业开发说明](https://shardingsphere.apache.org/elasticjob/current/cn/user-manual/usage/job-api/job-interface/)

### 3. 最前面的数据一直失败怎么办

若永久失败数据一直占据待处理集合的前几位，可能影响后续数据推进。生产方案可增加 `next_retry_at`、重试次数上限、错误分类和人工处理状态，让本轮暂不具备重试条件的数据退出当前可执行集合。

当前扩展关闭故障，用来单独验证批量边界；基础演示仍展示手动修复后补偿。自动退避、次数上限与人工处理队列尚未实现。

## 四、可选扩展：10 秒触发，15 秒才执行完（约 5 分钟）

这是独立的时间线练习，当前案例未自动注入慢任务，也未开启 `misfire` 或 `failover`。

先画出 0 秒开始、10 秒再次到点、15 秒上一轮结束的时间线，再按固定版本核对参数并设计实验。不要把普通 `setInterval` 发起异步请求的重叠行为直接当成 ElasticJob 的调度规则。

| 现象 | 要讨论的机制 | 不能直接推出什么 |
| --- | --- | --- |
| 上一轮未结束，错过本次触发 | `monitorExecution`、`misfire` | 不等于重试某笔失败订单 |
| 任务执行节点宕机 | `failover` 和下一轮重新分片 | 不保证恢复上次 Java 调用栈，也不消除重复副作用 |
| 节点正常，某笔业务超时 | 业务错误分类与补偿策略 | LOG 错误处理器不等于自动重试成功 |

官方说明中，错过任务重执行可在上一轮结束后继续执行逾期任务；失效转移面向故障节点未完成分片的接管。实验应单独准备慢任务、故障节点和业务验证，不直接修改主讲案例去临时碰运气。[错过任务重执行](https://shardingsphere.apache.org/elasticjob/current/cn/features/misfire/)、[失效转移](https://shardingsphere.apache.org/elasticjob/current/en/features/failover/)

## 五、可选扩展：停机两天，如何补历史窗口（约 5 分钟）

“再次触发任务”只回答现在要执行一次，不会自动定义它应该处理哪两天的数据。建议以“补昨天账单”为例，把业务日期作为明确参数：

```json
{"businessDate":"2026-10-20"}
```

以上为未来参数设计示意。当前 Job 只接受公共参数 `pending`，不能直接把这段 JSON 输入当前案例。

可以讨论以下设计：

1. 用业务时区定义日期窗口，如左闭右开的开始时间到结束时间。
2. 保存业务窗口的执行与完成记录，识别遗漏窗口，而不只依赖触发日志。
3. 为漏掉的日期分别提交补跑，明确目标范围、核对结果和重复处理约束。
4. 迟到数据通过回看或对账规则处理，不能因为窗口曾标记完成就永远忽略。

类比前端：“定时器负责什么时候发请求，请求参数决定查询哪一页、哪个日期。”调度时间与业务数据范围是不同维度。

## 六、讲完后检查什么

- 听众能算出三个分片每片 100，第一轮上限为 300。
- 能解释一轮成功结束时为什么还可能有积压。
- 能说出轮询待处理集合时，状态推进与分页跳过之间的关系。
- 能区分当前已实现的分批实验，与未实现的流式处理、自动重试和历史窗口补跑。
