# 配置中心扩展实验与实践

这篇是 [[配置中心分享讲稿]] 的独立扩展。优先讲断网与重启实验，约 8 分钟；资源刷新、用户灰度放在附录按需选讲。原主体仍为 37 分钟，加入实验后为 45 分钟，另留 5 分钟问答。首次启动和构建在会前完成。

## 一、先问三个不同的问题

“配置中心挂了，应用会不会挂？”不能直接回答会或不会。先判断是运行中的应用、同一容器重新启动，还是没有缓存的新实例。

| 状态 | 拥有什么 | 本案例的结论 |
| --- | --- | --- |
| Java 进程已经运行 | 已校验的内存快照 | Nacos 停止后，列表继续使用原快照 |
| 同一容器重新启动 | 原进程内存已丢失，容器可写层中的 SDK 缓存仍在 | 当前读取接口不回退到该缓存，启动失败 |
| 全新探针容器启动 | 没有上次内存，也没有旧容器中的缓存 | 取不到有效初始配置，启动失败 |

这些结论针对本案例 **Nacos 客户端 2.5.1 + `getConfigAndSignListener`**，不是所有 Nacos 接入方式的统一行为。

## 二、8 分钟操作流程

在本篇 `案例/` 目录操作。普通案例先按 [[配置中心演示手册]] 启动并验证；开发甲、乙对应 8081、8082 端口。

### 1. 准备可观察的状态（约 2 分钟）

在配置演示台发布开发环境：列表开启，每页 3。确认两个开发实例返回 3 笔，并记下启动标识。

查看实例甲的 SDK 磁盘文件：

```bash
docker compose exec -T app-a find /tmp/nacos/config -type f
```

应能看到 `snapshot-tenant/share-dev/ORDER_SERVICE/order-list.yaml`。当前镜像把 Java 的 `user.home` 设为 `/tmp`，快照位于容器可写层；它不是 Compose 命名卷。

讲述：“前端页面内存、浏览器持久存储和服务器上的数据是不同层次；这里的内存快照、容器磁盘缓存、配置中心也要分别看。”

### 2. 停止 Nacos，观察运行中的业务（约 2 分钟）

```bash
docker compose stop nacos
```

再次请求：

```bash
curl http://localhost:8081/api/orders
curl http://localhost:8082/api/orders
```

列表仍返回 3 笔，原进程启动标识不变。原因是业务读取已经采用的内存快照，不需要每次请求都同步访问 Nacos。

此时无法正常发布新配置。页面的 `lastError` 只反映业务配置解析或校验错误，不是 SDK 连接健康指标；本案例未实现连接中断告警和配置过期策略。

### 3. 重启同一容器，再启动一个全新探针（约 2 分钟）

```bash
docker compose restart app-a
docker compose ps -a app-a
docker compose logs --tail 80 app-a
```

等待日志出现本轮启动异常。实例甲取不到远程初始配置，启动失败；因为配置了 `restart: unless-stopped`，可能显示反复重启。此时 8081 页面不可用，可以继续观察未重启的实例乙。随后停止实例甲的重启循环：

```bash
docker compose stop app-a
```

启动没有旧缓存的探针：

```bash
docker compose --profile experiments up -d --no-deps app-cold
docker compose ps -a app-cold
docker compose logs --tail 80 app-cold
```

等待探针以非零退出码退出。该服务没有映射宿主机端口，也不自动重启。`--no-deps` 用于避免 Compose 自动把刚停掉的 Nacos 重新启动，才能保持实验条件。

### 4. 恢复并解释结果（约 2 分钟）

```bash
docker compose start nacos
docker compose ps nacos
```

等 Nacos 显示 healthy 后：

```bash
docker compose start app-a
docker compose --profile experiments rm -s -f app-cold
```

实例甲恢复就绪后，在演示台点击“恢复初始配置”。普通 `restart` 保留容器可写层；删除并重建容器通常会失去其中的数据。不能用“重启容器”来证明“全新容器已有缓存”。

Windows PowerShell 中的接口命令使用 `curl.exe`，其余 Docker 命令相同。

## 三、为什么缓存文件在，重启还是失败

这不是“缓存文件一定没写好”。Nacos 2.5.1 的源码中，`getConfigAndSignListener` 直接查询服务端并注册监听；`getConfig` 的内部读取路径则包含异常后读取本地快照的逻辑。**接入 API 不同，故障行为可能不同。**

当前案例保留“启动必须取得并校验有效配置”的接入方式，让两条路径的区别可观察。如果项目需要离线启动，应另行设计并验证读取策略、可持久化缓存、配置时效和恢复后的重新订阅。仅挂载缓存目录不能改变读取接口本身的行为。

还要分清：SDK 保存的原始配置文本与业务最后接受的有效快照不是同一层。原始文本即使被缓存，也仍须重新做业务校验，不能把 SDK 缓存当作“已经通过业务验证”的证明。

依据：[Nacos 2.5.1 配置读取实现](https://github.com/alibaba/nacos/blob/2.5.1/client/src/main/java/com/alibaba/nacos/client/config/NacosConfigService.java)、[本地快照实现](https://github.com/alibaba/nacos/blob/2.5.1/client/src/main/java/com/alibaba/nacos/client/config/impl/LocalConfigInfoProcessor.java)。

Apollo 官方客户端提供本地文件缓存机制；是否能在故障下恢复，还要核对缓存是否存在、目录权限与部署策略。当前 Docker 案例未部署 Apollo，不能用上述 Nacos 实验直接代替 Apollo 的行为验证。[Apollo 客户端说明](https://github.com/apolloconfig/apollo/blob/master/docs/en/client/java-sdk-user-guide.md#123-local-cache-path)

### 讲师收尾话术

> 配置中心不可用，并不等于运行中的业务立即不可用。已经采用的配置可以留在内存中。但当进程重新启动，内存就没了，此时能否恢复取决于具体读取接口和缓存策略。真正要设计的是：取不到新配置时能否继续、最多接受多旧的配置、哪些配置必须立即失效，以及恢复后怎样确认重新跟上发布版本。

配置过期后继续使用、关闭某功能或阻止启动，都要按具体业务选择。本案例没有自动配置过期、持久化业务有效快照或跨实例统一失效能力。

## 四、可选扩展：参数刷新不等于资源刷新（约 4 分钟）

现有 `page-size` 在每次请求开始时读取，因此容易动态生效。换成数据库连接池、HTTP 客户端或线程池，就要检查资源如何创建和更新。

举例：“把 HTTP 超时从 30 秒改成 3 秒，配置页面已更新，为什么调用还是等了 30 秒？”

| 位置 | 可能发生什么 | 应核对的证据 |
| --- | --- | --- |
| 配置仓库 | 参数已变为 3 秒 | 实例当前采用的配置版本 |
| 已创建的客户端 | 仍保留创建时的 30 秒参数 | 具体组件的更新接口和对象生命周期 |
| 正在执行的请求 | 已经使用旧客户端或旧参数 | 超时实际行为和请求日志 |

处理方式取决于组件：支持原地更新的，调用相应更新能力；需要重建的，设计新对象验证、引用切换、旧对象释放与失败恢复。不能把“替换参数快照”直接视为“安全替换所有资源”。这里是设计推演，案例没有新增真实连接池或 HTTP 客户端刷新实现。

## 五、可选扩展：从全量开关到用户灰度（约 4 分钟）

原案例开关针对整个应用实例。若希望先对约 10% 的用户开放，需要业务按用户身份稳定分桶。

```java
// 逻辑示意；stableHash 需要明确算法、输入编码与固定规则，不是案例已有方法。
int bucket = Math.floorMod(stableHash(userId), 100);
boolean enabledForUser = globalEnabled && bucket < rolloutPercent;
```

- 同一个用户在规则不变时得到稳定结果，避免每次请求随机决定。
- 将比例从 10 调到 20，原来命中的分桶仍在范围内；小样本实际比例未必恰好等于设定值。
- 前后端若各自计算，必须统一哈希与身份规则；也可以由后端统一决定并返回允许公开的结果。
- 平台按客户端实例灰度发布，与业务按用户灰度是不同维度。
- 功能开关决定功能是否开放，访问资格仍由后端权限校验。

上述用户灰度、资源刷新均为下一阶段设计练习，当前可运行扩展只包括断网与重启实验。实际验证结果见 [[配置中心验证记录]]、[[配置中心断网重启验证输出.txt]]。
