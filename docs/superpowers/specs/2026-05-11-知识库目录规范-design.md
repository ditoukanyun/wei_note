# 知识库目录规范设计

## 背景

`40_知识库` 已经积累了后端开发、前端开发、AI、Python 编程、通用技能、交易、DevOps 等内容。当前结构能支持阅读和查找，但存在几类维护问题：

- 领域入口和专题索引风格不统一，例如后端、前端已有 MOC，AI 缺少清晰总入口。
- 原子概念、课程型资料、实践清单、工具资源和迁移内容混在同一层级。
- 部分目录有 `img`、`images`、`02_Resources` 等附件/资源目录，但缺少统一放置规则。
- 已有 `99_系统/模板/Wiki_Template.md` 和 `99_系统/数据库/Knowledge.base`，但缺少面向新增知识的目录规范。

目标是建立一套轻量、可持续维护的规范，先指导新增内容和后续渐进整理，不要求立刻大规模迁移旧文件。

## 目标

本次设计产出两份规范文件：

- `99_系统/规范/知识库目录规范.md`：正式规范，作为唯一规则来源。
- `40_知识库/知识库目录规范.md`：入口摘要，方便在知识库目录内快速查看，并跳转到正式规范。

正式规范需要同时包含“待补知识点清单”，按主要领域列出知识缺口，方便后续逐步补齐。

## 非目标

- 不在本阶段批量移动、重命名已有知识库文件。
- 不把每个领域拆成独立规范文件。
- 不替换现有 `Wiki_Template.md`，只补充它在目录治理中的使用约定。
- 不调整 `Knowledge.base` 的数据库视图，除非后续实施时发现必须修正明显错误。

## 方案选择

采用“主规范 + 入口摘要”的轻量规范方案。

### 方案优点

- 规则只维护在 `99_系统/规范/知识库目录规范.md`，避免两份文件长期分叉。
- `40_知识库/知识库目录规范.md` 只保留摘要、常用规则和正式规范链接，便于日常使用。
- 旧文件不强制立刻迁移，降低整理成本。
- 待补知识点清单放在正式规范内，能把目录规则和内容缺口放在同一个维护入口。

### 放弃的方案

- 强治理方案：一次性规定所有文件迁移、命名和重构，短期成本高。
- 领域路线图方案：每个领域单独建立规范，细节充分但规则容易分散。

## 文件职责

### `99_系统/规范/知识库目录规范.md`

正式规范包含以下章节：

1. 规范目标：说明新增优先遵守、旧内容逐步整理。
2. 目录职责：定义领域目录、专题目录、MOC、原子概念、实践清单、资源附件、迁移内容的放置规则。
3. 命名规则：规定中文稳定命名、专题名、MOC 命名、附件目录命名和避免重复概念的规则。
4. MOC 规则：每个大领域至少一个 MOC，负责导航、学习路径、相关概念连接和更新入口。
5. frontmatter 规则：沿用 `Wiki_Template.md`，明确 `area`、`tags`、`created` 的使用方式。
6. 新增知识判断流程：新增前判断它是原子概念、专题索引、实践清单、资源材料还是项目内容。
7. 渐进整理规则：旧内容不强制移动，遇到重复、缺 MOC、附件散落时逐步收敛。
8. 待补知识点清单：按领域列出建议补齐的知识点。

### `40_知识库/知识库目录规范.md`

入口摘要包含以下章节：

1. 正式规范链接：指向 `[[99_系统/规范/知识库目录规范|知识库目录规范]]`。
2. 快速规则：列出新增知识时最常用的判断规则。
3. 领域入口：链接后端、前端、AI、Python、通用技能等主要 MOC。
4. 待补知识点提示：说明完整清单在正式规范中维护。

入口摘要不重复完整规则，避免和正式规范冲突。

## 目录模型

知识库按“领域 -> 专题 -> 知识点”理解：

- 领域目录：`40_知识库/后端开发`、`40_知识库/前端开发`、`40_知识库/AI`、`40_知识库/通用技能` 等。
- 专题目录：某个领域下的稳定主题，例如 `后端开发/消息队列`、`前端开发/React`、`AI/AI相关/RAG技术`。
- MOC：领域或专题的导航入口，例如 `后端开发 MOC.md`、`前端开发 MOC.md`、`MOC-Python编程.md`。
- 原子概念：单一概念或方法，例如 `幂等性.md`、`OAuth2 与 OIDC 核心概念.md`。
- 实践清单：面向执行的检查表或流程，例如交易检查清单、部署清单。
- 资源附件：图片、材料、外部资源索引，优先放在对应专题的资源目录内。

## 待补知识点清单设计

正式规范内维护一个“待补知识点清单”，先按领域分组，不要求每个条目立即创建文件。初始建议如下：

- AI：AI MOC 总入口、Agent 架构总览、RAG 评估、向量数据库选型、模型上下文工程、AI 安全与权限边界、AI Coding 工作流对比。
- 后端开发：API 契约治理、数据库迁移规范、服务间调用治理、任务调度、文件存储、配置中心、审计日志、生产故障复盘模板。
- 前端开发：TypeScript 类型设计、组件 API 设计、状态管理选型、前端错误监控、可访问性检查清单、设计系统落地流程、端到端测试。
- 通用技能：技术写作、Code Review 方法、需求澄清、调试方法论、任务拆解、个人知识管理流程。
- 交易：交易复盘模板、风险控制规则、仓位管理、策略验证、情绪记录指标。
- DevOps/工具：环境变量管理、密钥管理、发布回滚、日志留存、备份恢复、开发工具标准配置。

后续整理时，如果某个待补条目已经有零散笔记，优先创建 MOC 或汇总入口，而不是重复写新笔记。

## 维护规则

- 新增内容优先遵守规范，旧内容按接触频率逐步整理。
- 同一概念出现多个文件时，保留更清晰的中文概念名，其他文件用链接、别名或迁移说明收敛。
- 某领域文件超过约 20 篇但没有 MOC，列为优先补 MOC。
- 资源附件不直接堆在领域根目录，放到对应专题的 `资源`、`images` 或既有附件目录中。
- 规范变更只改正式规范；入口摘要只同步必要摘要和链接。

## 验证方式

实施完成后检查：

- 两份文件都存在，且互相链接关系清晰。
- `99_系统/规范/知识库目录规范.md` 是唯一完整规则来源。
- `40_知识库/知识库目录规范.md` 没有重复完整规则，只做入口摘要。
- 正式规范包含待补知识点清单。
- 新文件 frontmatter 后没有多余空行。
- 文件内容全部使用中文。

## 后续实施边界

用户确认本设计后，下一步进入实施计划，计划应覆盖：

- 创建 `99_系统/规范` 目录。
- 新增正式规范文件。
- 新增知识库入口摘要文件。
- 检查 Obsidian wikilink 和 frontmatter。
- 不处理无关的现有未提交文件。
