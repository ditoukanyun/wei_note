# 稳定哈希

## 定义

稳定哈希是在灰度、分流或分桶场景中，根据稳定输入计算固定 bucket 的方法。只要输入不变，同一用户或实体的命中结果就保持一致。

## 解决的问题

- 百分比灰度中不能使用随机数，否则同一用户多次请求会命中不同路径。
- 放量比例变化时，需要用户集合可预测地扩展，而不是全量重新洗牌。
- 多服务、多实例需要对同一用户得到一致分桶结果。

## 要点

- 输入通常包含规则 key 和用户 ID，例如 `flagKey:userId`。
- 输出通常映射到 0-99 或 0-9999 的 bucket，用于百分比灰度。
- 与随机数不同，稳定哈希不会让同一用户在多次请求间反复切换路径。
- 调整灰度比例时，低 bucket 用户会逐步进入新版本。
- 常用于[[灰度发布]]、[[Feature Flag]]、A/B 实验和一致性路由。
- 分桶输入要稳定且粒度明确，例如用户级、租户级或设备级。

## 示例

`CRC32("new-checkout:1001") % 100 = 17`，当 rolloutPercent 为 30 时用户命中新功能；当 rolloutPercent 为 10 时不命中。

对应模块：[[SpringBoot/35-SpringBoot-FeatureFlag与灰度发布]]。

## 设计取舍

| 选择 | 影响 |
|---|---|
| 用户 ID 分桶 | 同一用户体验稳定 |
| 租户 ID 分桶 | 同一企业或组织整体命中同一版本 |
| 设备 ID 分桶 | 未登录用户也能稳定命中 |
| 更大 bucket 范围 | 放量比例更精细，但排查时需要展示 bucket |

## 易错点

- 使用当前时间、请求 ID 等不稳定输入参与哈希。
- 不同语言或服务使用不同哈希算法，导致分桶结果不一致。
- 调整规则 key 后所有用户重新分桶，造成灰度人群突变。
