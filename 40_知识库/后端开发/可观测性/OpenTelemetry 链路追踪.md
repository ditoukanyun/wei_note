# OpenTelemetry 链路追踪

## 定义

OpenTelemetry 是开放可观测性标准，提供 Trace、Metric、Log 的采集规范和 SDK，其中链路追踪用于还原一次请求跨服务调用路径。

## 要点

- Trace 表示完整调用链。
- Span 表示链路中的一次操作。
- TraceId 用于关联跨服务日志和调用。
- 采样策略影响成本和排障精度。

## 接入流程

```mermaid
flowchart LR
  A[应用 SDK 或 Agent] --> B[生成 Trace 和 Span]
  B --> C[注入 Trace Context]
  C --> D[Collector 接收处理]
  D --> E[导出到追踪后端]
  E --> F[查询慢链路和错误链路]
```

## 实践检查清单

- HTTP、RPC、消息队列是否正确传播 Trace Context。
- 关键业务步骤是否补充自定义 Span 和业务标签。
- 日志中是否输出 TraceId，便于从日志跳转到链路。
- 采样策略是否区分高频正常请求和异常请求。
- Collector 是否统一做脱敏、批量发送和失败重试。

## 案例

一次下单请求经过网关、订单、库存、支付三个服务。链路追踪能显示库存服务耗时突然升高，并进一步定位到数据库查询 Span，而不是只看到网关接口变慢。

## 接入边界

OpenTelemetry 的价值在于统一信号和上下文传播，不在于替代所有观测工具。接入时应先覆盖入口请求、关键下游调用、数据库、缓存和消息队列，再逐步补业务 Span。过早给每个小函数都加 Span，会增加成本和噪音。

Trace Context 传播是链路追踪成败的关键。HTTP、RPC、消息队列和异步任务都要明确如何传递 TraceId，否则链路会在跨边界时断开，排查仍然只能靠人工拼日志。

## 常见误区

- 只接入入口服务，跨服务调用没有上下文传播。
- 给 Span 添加过多高基数字段，例如完整用户输入，导致存储成本失控。
- 把链路追踪当日志系统使用，忽略指标告警和日志细节。
