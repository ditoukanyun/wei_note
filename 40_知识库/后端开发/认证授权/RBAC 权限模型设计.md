# RBAC 权限模型设计

## 定义

RBAC 是基于角色的访问控制模型，通过用户、角色、权限之间的关系管理系统访问能力。

## 要点

- 用户被分配角色，角色拥有权限。
- 权限通常表达为资源和动作的组合。
- 角色层级和数据范围会显著增加复杂度。
- 权限变更需要审计和最小权限原则。

## 模型结构

```mermaid
flowchart LR
    U["用户 User"] --> UR["用户-角色关系"]
    UR --> R["角色 Role"]
    R --> RP["角色-权限关系"]
    RP --> P["权限 Permission"]
    P --> A["资源 + 动作"]
```

## 案例

后台订单系统可以定义：

- 角色：客服、运营、管理员。
- 权限：`order:read`、`order:refund`、`order:export`。
- 数据范围：客服只能看自己负责店铺，管理员可看全部。

如果只做角色判断，不做数据范围校验，用户可能通过改订单 ID 访问不属于自己的资源，形成越权。

## 检查清单

- 权限是否表达为资源和动作，而不是只靠页面菜单。
- 是否有数据范围，例如部门、租户、店铺、本人。
- 是否遵守最小权限原则。
- 权限变更是否记录审计日志。
- 服务端是否做资源级校验，前端隐藏按钮不能替代授权。
- 是否和 [[API 安全基础]] 的越权检查一起设计。

## 常见误区

- 只控制菜单显示，不控制 API 访问。
- 角色直接写死在代码里，后续扩展困难。
- 没有数据范围，导致同角色用户互相访问数据。
- 权限变更不审计，问题发生后无法追踪。

## 落地建议

权限编码建议稳定、可读，例如 `order:read`、`order:refund`、`user:disable`。服务端鉴权时不仅判断用户是否有动作权限，还要判断资源是否属于用户的数据范围。

## 掘金补充

掘金文章《前端 RBAC 权限方案》把权限粒度拆成页面权限、内容权限和更细的控件权限，这个视角可以补充前后端协作边界：前端可以根据用户角色或权限集生成菜单、过滤路由、隐藏按钮，但这些都只是体验层控制；真正的授权仍必须在服务端 API 和资源访问处校验。

对于中后台系统，前端配置里不要长期硬编码角色名，可以逐步抽象成资源动作或权限 Key，例如 `view`、`edit`、`export`、`publish`。页面级拦截负责 403/404 和菜单可见性，内容级权限负责组件展示，接口级权限负责安全兜底，三层缺一不可。

文章中动态角色方案的重点是稳定的 `resourceKey`：不要用容易变化的路由 path 当权限资源标识，因为前端页面结构会调整，后端接口也可能复用。更稳的做法是让菜单、页面、按钮和接口都映射到稳定资源 Key，再由角色勾选资源动作。一个用户有多个角色时，通常按权限并集处理，但接口被多个页面复用时要提前定义并集还是交集，避免越权或误拦截。

微前端场景下，权限最好收敛到主应用：主应用控制子应用加载、菜单和页面访问，子应用通过注入的权限查询函数处理内容权限，减少每个子应用各自实现一套鉴权逻辑。
