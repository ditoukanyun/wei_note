# CI-CD 流水线

## 定义

CI-CD 流水线是把代码检查、测试、构建、制品发布、部署、验证和回滚串成自动化流程的工程系统。它的目标是让每次变更都能被快速验证、可追踪交付，并在出问题时有明确回退路径。

## 基本阶段

- 触发：推送代码、合并请求、打标签或手动发布。
- 检查：格式、Lint、类型检查、单元测试和安全扫描。
- 构建：前端静态资源、后端二进制包或容器镜像。
- 发布：上传制品、推送镜像、记录版本和变更日志。
- 部署：滚动发布、蓝绿发布、金丝雀发布或手动审批。
- 验证：健康检查、烟雾测试、监控指标和日志检查。
- 回滚：保留旧版本制品和配置，能快速恢复。

## 实践要点

- CI 必须快，慢检查可以拆到夜间或发布前门禁。
- CD 必须可观测，部署后要能看到错误率、延迟和关键业务指标。
- 环境变量、密钥和配置不能硬编码进仓库。
- 前端和后端都应产出可追踪版本，便于问题定位。

## 流水线流程

```mermaid
flowchart LR
    A["提交代码"] --> B["Lint / 类型检查"]
    B --> C["单元测试 / 集成测试"]
    C --> D["构建制品或镜像"]
    D --> E["安全扫描"]
    E --> F["部署到测试/预发"]
    F --> G["烟雾测试"]
    G --> H["灰度或生产发布"]
    H --> I["监控验证 / 回滚"]
```

流水线的价值是把发布风险前移，并让每次发布都有证据链：代码版本、构建产物、部署环境、验证结果和回滚路径。

## 前后端差异

- 前端重点关注类型检查、构建产物体积、资源缓存、静态资源发布和回滚。
- 后端重点关注单元测试、集成测试、镜像构建、数据库迁移、健康检查和运行指标。
- 全栈项目要明确接口契约检查，避免前端构建成功但接口变更导致运行失败。

## 检查清单

- 每次构建是否能追踪到 Git Commit、镜像标签和变更人。
- 密钥是否来自 CI Secret 或密钥系统，而不是仓库文件。
- 测试是否覆盖关键路径，失败后是否阻断合并或发布。
- 部署后是否自动检查健康端点、错误率和核心业务指标。
- 回滚是否使用已验证旧制品，而不是临时重新构建。
- 是否配合 [[Feature Flag]] 降低大功能一次性发布风险。
