# 分布式事务

分布式事务处理跨服务、跨数据库或跨消息系统的一致性问题。工程上常用最终一致性、Saga、Outbox 和补偿机制替代强同步事务。

## 相关概念

- [[最终一致性]]
- [[Saga]]
- [[Transactional Outbox]]
- [[SpringBoot/25-SpringBoot-多数据源与事务边界|多数据源与事务边界]]

## 方案选择

- 本地事务：单库单服务内优先使用，成本最低。
- Outbox：业务写入和事件记录在同一个本地事务中完成，再异步投递消息。
- Saga：把长事务拆成多个本地事务，每一步都有补偿动作。
- TCC：Try、Confirm、Cancel 明确预留资源，适合资金、库存等强约束场景。

## 处理流程

```mermaid
flowchart LR
  A[业务请求] --> B[本地事务写业务表]
  B --> C[写 Outbox 事件]
  C --> D[异步发布消息]
  D --> E[下游幂等消费]
  E --> F[状态回查与补偿]
```

## 实践检查清单

- 是否先确认真的需要跨服务事务，而不是服务边界划错。
- 每个步骤是否可重试、可幂等、可回查。
- 失败状态是否有补偿任务、人工介入入口和审计记录。
- 消息发送、消费和业务状态是否能通过统一标识串起来。
- 用户界面是否能表达处理中、成功、失败和待补偿状态。

## 常见误区

- 追求强一致性，导致链路耦合、锁时间过长和可用性下降。
- 只设计正向流程，缺少取消、超时、重复消息和部分失败处理。
- 补偿逻辑没有测试，真正故障时反而制造二次错误。
