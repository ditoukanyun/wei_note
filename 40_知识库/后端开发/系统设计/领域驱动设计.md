# 领域驱动设计

## 定义

领域驱动设计是把复杂业务系统围绕业务领域建模的设计方法。它强调通用语言、限界上下文、聚合、实体、值对象、领域服务和领域事件，让代码结构尽量贴近业务规则，而不是只围绕数据库表和技术分层组织。

## 核心概念

- **通用语言**：业务、产品、开发和测试共同使用的概念体系。
- **限界上下文**：一组模型只在特定业务边界内保持一致语义。
- **聚合**：维护业务不变量的一组对象边界。
- **实体**：有连续身份的业务对象。
- **值对象**：由属性值定义，没有独立身份。
- **领域事件**：业务上已经发生且值得其他模块感知的事实。

## 使用边界

- 适合业务规则复杂、团队协作多、模型长期演进的系统。
- 不适合简单 CRUD 被过度建模；过早引入会增加理解成本。
- DDD 不等于微服务，单体系统也可以使用清晰的领域模型。

## 建模流程

```mermaid
flowchart LR
  A[梳理业务流程] --> B[提炼通用语言]
  B --> C[划分限界上下文]
  C --> D[识别聚合和不变量]
  D --> E[落到代码和事件]
```

## 实践检查清单

- 是否和业务方一起确认核心名词和规则。
- 限界上下文是否解决语义边界，而不是照搬组织架构。
- 聚合是否围绕一致性边界设计。
- 领域事件是否表达已经发生的业务事实。
- 是否避免简单 CRUD 过度建模。

## 案例

电商系统中“订单”在交易上下文表示购买承诺，在履约上下文表示发货任务，在财务上下文表示结算依据。三个上下文可以共享 ID，但模型语义不应强行合并。

## 常见误区

- 认为 DDD 等于四层架构模板。
- 一上来拆微服务，领域模型还没稳定。
- 聚合过大，所有操作都互相锁定，系统变慢。
