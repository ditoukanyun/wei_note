# API聚合

API 聚合是在服务端或 BFF 层把多个下游接口结果组合成更适合前端页面消费的接口。

## 相关概念

- [[BFF]]
- [[前后端接口契约]]
- [[超时控制]]
- [[降级]]

## 聚合流程

```mermaid
flowchart LR
  A[前端页面请求] --> B[BFF 接口]
  B --> C[并发调用下游]
  C --> D[合并和裁剪字段]
  D --> E[返回页面模型]
```

## 实践检查清单

- 聚合接口是否围绕页面模型设计，而不是简单转发多个接口。
- 下游调用是否有超时、并发控制和部分失败降级。
- 是否避免在 BFF 中沉淀核心业务规则。
- 响应字段是否有版本管理，避免前端和后端耦合过紧。
- 是否记录每个下游接口耗时，便于定位慢点。

## 案例

订单详情页需要订单、物流、优惠券和客服状态。BFF 可以并发请求多个服务并返回前端所需结构；若客服状态失败，可返回默认值并标记部分数据不可用。

## 设计边界

API 聚合应服务页面体验，而不是把所有下游接口简单拼成一个大响应。聚合层可以裁剪字段、合并模型、处理部分失败和隐藏下游复杂度，但不应承载核心业务规则，否则 BFF 会变成难复用的新业务单体。

聚合接口还要有超时预算。多个下游并发时，总响应时间由最慢依赖决定；必要时应做缓存、降级、并发限制和字段级可选返回。

BFF 的返回模型应贴近页面，但仍要保持版本和兼容意识。页面迭代频繁时，可以通过新增字段和灰度接口减少前后端互相阻塞。

## 常见误区

- BFF 变成新的单体业务层，承载大量核心规则。
- 一个下游慢接口拖垮整个页面响应。
- 聚合接口没有缓存和降级，峰值时放大下游压力。

## 复盘问题

- 页面是否真的需要一次性聚合这些字段。
- 下游部分失败时，前端是否能展示可理解的降级状态。
