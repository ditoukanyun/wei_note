# Outbox Pattern 事务消息

## 定义

Outbox Pattern 是把业务数据变更和待发送消息写入同一个本地事务，再由异步任务可靠投递消息的模式。

## 要点

- 避免数据库事务和消息队列之间的双写不一致。
- Outbox 表是消息投递的中间事实来源。
- 投递端需要重试、去重和状态追踪。

## 相关概念

- [[Transactional Outbox]]
- [[最终一致性]]
- [[消息可靠性：确认、重试与死信队列]]

## 投递流程

```mermaid
flowchart LR
  A[业务写入] --> B[同事务写 Outbox]
  B --> C[投递任务扫描]
  C --> D[发送到消息队列]
  D --> E[标记已发送]
  E --> F[消费者幂等处理]
```

## 实践检查清单

- Outbox 表是否包含消息 ID、类型、状态、重试次数和创建时间。
- 业务数据和 Outbox 写入是否在同一个本地事务中。
- 投递任务是否支持重试、退避和并发控制。
- 消费端是否按消息 ID 幂等处理。
- 是否有失败消息的告警和人工补偿入口。

## 案例

订单创建时同时写订单表和 Outbox 事件表。后台任务把事件投递到 Kafka，成功后更新状态。即使服务在提交事务后崩溃，重启后仍能从 Outbox 表继续投递。

## 常见误区

- 业务写库和发消息分成两个无保护步骤。
- Outbox 只写不清理，表无限增长。
- 投递成功但标记失败时没有去重设计，造成重复消费。
