# 5种 ADK Agent Skill 设计模式

> 本文整理自 Google Cloud Tech 发布的技术文章，介绍了每个 ADK 开发者都应该了解的 5 种 Agent Skill 设计模式。

## 核心观点

当谈到 `SKILL.md` 时，开发者往往过于关注格式——如何让 YAML 正确、如何结构化目录、如何遵循规范。但随着超过 30 种 Agent 工具（如 Claude Code、Gemini CLI 和 Cursor）都采用相同的布局，格式问题实际上已经解决了。

现在的挑战是**内容设计**。规范解释了如何打包一个 skill，但对如何构建内部的逻辑却没有任何指导。例如，一个封装 FastAPI 规范的 skill 与一个四步文档流水线 skill 的运作方式完全不同，尽管它们的 `SKILL.md` 文件外观看起来几乎一样。

通过研究 Anthropic 仓库、Vercel 和 Google 内部指南等生态系统中的 skill 构建方式，可以总结出五种重复出现的设计模式。

---

## 模式一：工具包装器 (Tool Wrapper)

### 核心思想

工具包装器让你的 Agent 成为特定库的即时专家。与其将 API 约定硬编码到系统提示词中，不如将它们打包成一个 skill。Agent 只在真正使用该工具时才加载这些上下文。

### 实现机制

- `SKILL.md` 监听用户提示中的特定库关键词
- 动态从 `references/` 目录加载内部文档
- 将这些规则作为绝对真理应用

这是将团队内部编码规范或特定框架最佳实践直接分发到开发者工作流程中的机制。

### 示例：FastAPI 专家

```yaml
# skills/api-expert/SKILL.md
---
name: api-expert
description: FastAPI 开发最佳实践和规范。在构建、审查或调试 FastAPI 应用程序、REST API 或 Pydantic 模型时使用。
metadata:
  pattern: tool-wrapper
  domain: fastapi
---

你是 FastAPI 开发专家。将这些约定应用于用户的代码或问题。

## 核心约定

在开始审查或编写代码时加载 `references/conventions.md` 获取完整的 FastAPI 最佳实践列表。

## 审查代码时
1. 加载约定参考文档
2. 逐条检查用户代码是否符合约定
3. 对于每个违规项，引用具体规则并建议修复

## 编写代码时
1. 加载约定参考文档
2. 严格遵循每条约定
3. 为所有函数签名添加类型注解
4. 对依赖注入使用 Annotated 风格
```

### 适用场景

- 团队内部编码规范分发
- 特定框架最佳实践
- 技术栈专有知识封装

## 模式二：生成器 (Generator)

### 核心思想

如果说工具包装器是应用知识，那么生成器则是强制一致的输出。如果你苦于 Agent 每次运行都生成不同的文档结构，生成器通过编排一个"填空"过程来解决这个问题。

### 实现机制

利用两个可选目录：
- `assets/` - 存放输出模板
- `references/` - 存放风格指南

指令充当项目经理，告诉 Agent：
1. 加载模板
2. 阅读风格指南
3. 询问用户缺失的变量
4. 填充文档

### 示例：技术报告生成器

```yaml
# skills/report-generator/SKILL.md
---
name: report-generator
description: 生成结构化的 Markdown 技术报告。在用户要求编写、创建或起草报告、摘要或分析文档时使用。
metadata:
  pattern: generator
  output-format: markdown
---

你是技术报告生成器。严格遵循以下步骤：

**步骤 1**：加载 `references/style-guide.md` 获取语气和格式规则。

**步骤 2**：加载 `assets/report-template.md` 获取所需的输出结构。

**步骤 3**：询问用户任何缺失的填充模板所需信息：
- 主题或课题
- 关键发现或数据点
- 目标受众（技术型、高管层、普通读者）

**步骤 4**：按照风格指南规则填充模板。模板中的每个部分都必须出现在输出中。

**步骤 5**：将完成的报告作为单个 Markdown 文档返回。
```

### 适用场景

- 生成可预测的 API 文档
- 标准化提交信息
- 脚手架项目架构
- 任何需要一致输出的场景

## 模式三：审查器 (Reviewer)

### 核心思想

审查器模式将"检查什么"与"如何检查"分离。与其在系统提示词中写一长串代码异味说明，不如将模块化的评分标准存放在 `references/review-checklist.md` 文件中。

### 实现机制

1. 用户提交代码
2. Agent 加载检查清单
3. 有条理地为提交内容评分
4. 按严重程度分组发现的问题

如果换成 Python 风格检查清单为 OWASP 安全检查清单，就能得到一个完全不同的专业审计——使用完全相同的 skill 基础设施。

### 示例：代码审查器

```yaml
# skills/code-reviewer/SKILL.md
---
name: code-reviewer
description: 审查 Python 代码的质量、风格和常见错误。在用户提交代码审查、询问代码反馈或需要代码审计时使用。
metadata:
  pattern: reviewer
  severity-levels: error,warning,info
---

你是 Python 代码审查器。严格遵循以下审查协议：

**步骤 1**：加载 `references/review-checklist.md` 获取完整的审查标准。

**步骤 2**：仔细阅读用户的代码。在批评之前先理解其用途。

**步骤 3**：将检查清单中的每条规则应用于代码。对于发现的每个违规项：
- 记录行号（或大致位置）
- 分类严重程度：error（必须修复）、warning（应该修复）、info（可以考虑）
- 解释**为什么**这是个问题，而不仅仅是**什么**错了
- 提出具体的修复建议和修正后的代码

**步骤 4**：生成结构化的审查报告，包含以下部分：
- **摘要**：代码做什么，整体质量评估
- **发现**：按严重程度分组（错误优先，然后警告，然后信息）
- **评分**：1-10 分并简要说明理由
- **前 3 建议**：最有影响力的改进点
```

### 适用场景

- 自动化 PR 审查
- 在人工审查前捕获漏洞
- 代码质量门禁
- 安全审计

## 模式四：反转 (Inversion)

### 核心思想

Agent 天生倾向于猜测和立即生成。反转模式颠覆了这种动态。不是用户驱动提示词而 Agent 执行，而是 Agent 充当**采访者**。

### 实现机制

依靠明确的、不可协商的准入指令（如"在所有阶段完成之前不要开始构建"）来强制 Agent 先收集上下文。

- 按顺序提出结构化问题
- 等待你的回答再进入下一阶段
- 直到获得完整的用户需求和部署约束画面后才合成最终输出

### 示例：项目规划器

```yaml
# skills/project-planner/SKILL.md
---
name: project-planner
description: 通过结构化问题收集需求后再生成计划来规划新软件项目。在用户说"我想构建"、"帮我规划"、"设计一个系统"或"开始一个新项目"时使用。
metadata:
  pattern: inversion
  interaction: multi-turn
---

你正在进行结构化的需求访谈。**在所有阶段完成之前不要开始构建或设计。**

## 第一阶段 —— 问题发现（一次只问一个问题，等待每个回答）

按顺序提问，不要跳过任何一个：

- Q1: "这个项目为用户解决了什么问题？"
- Q2: "主要用户是谁？他们的技术水平如何？"
- Q3: "预期规模如何？（每日用户数、数据量、请求率）"

## 第二阶段 —— 技术约束（仅在第一阶段完全回答后）

- Q4: "你将使用什么部署环境？"
- Q5: "你对技术栈有什么要求或偏好？"
- Q6: "有哪些不可协商的要求？（延迟、可用性、合规性、预算）"

## 第三阶段 —— 综合（仅在所有问题回答后）

1. 加载 `assets/plan-template.md` 获取输出格式
2. 使用收集到的需求填充模板的每个部分
3. 向用户展示完成的计划
4. 询问："这个计划准确捕捉了你的需求吗？你想修改什么？"
5. 根据反馈迭代直到用户确认
```

### 适用场景

- 项目启动和需求收集
- 复杂任务的需求澄清
- 防止过早优化的场景
- 需要充分了解约束条件的决策

## 模式五：流水线 (Pipeline)

### 核心思想

对于复杂任务，你不能承受跳过步骤或忽略指令的后果。流水线模式强制执行严格的、顺序的工作流程和硬性检查点。

### 实现机制

指令本身充当工作流程定义。通过实现明确的菱形门控条件（如需要用户批准才能从文档字符串生成阶段进入最终组装阶段），流水线确保 Agent 不能绕过复杂任务并呈现未验证的最终结果。

这个模式使用所有可选目录，只在特定步骤需要时拉入不同的参考文件和模板，保持上下文窗口干净。

### 示例：文档流水线

```yaml
# skills/doc-pipeline/SKILL.md
---
name: doc-pipeline
description: 通过多步流水线从 Python 源代码生成 API 文档。在用户要求为模块生成文档、生成 API 文档或从代码创建文档时使用。
metadata:
  pattern: pipeline
  steps: "4"
---

你正在运行文档生成流水线。按顺序执行每个步骤。**不要跳过步骤，如果某一步失败也不要继续。**

## 步骤 1 —— 解析与清单

分析用户的 Python 代码，提取所有公共类、函数和常量。将清单以检查清单形式呈现。询问："这是你想要记录的完整公共 API 吗？"

## 步骤 2 —— 生成文档字符串

对于每个缺少文档字符串的函数：
- 加载 `references/docstring-style.md` 获取所需格式
- 严格按照风格指南生成文档字符串
- 展示每个生成的文档字符串供用户批准

**在用户确认之前不要进入步骤 3。**

## 步骤 3 —— 组装文档

加载 `assets/api-doc-template.md` 获取输出结构。将所有类、函数和文档字符串编译成单个 API 参考文档。

## 步骤 4 —— 质量检查

根据 `references/quality-checklist.md` 审查：
- 每个公共符号都有文档
- 每个参数都有类型和描述
- 每个函数至少有一个使用示例

报告结果。在呈现最终文档之前修复问题。
```

### 适用场景

- 复杂文档生成
- 多阶段代码审查
- 需要严格质量控制的流程
- 有明确依赖步骤的工作流

## 如何选择正确的模式

每种模式回答不同的问题。使用以下决策树找到适合你用例的模式：

| 问题 | 选择模式 |
|------|----------|
| "如何让 Agent 了解 X？" | **工具包装器** —— 打包约定供按需加载 |
| "如何确保一致的输出？" | **生成器** —— 用模板和检查清单强制结构 |
| "如何系统地评估质量？" | **审查器** —— 按严重程度评分，参考结构化检查清单 |
| "如何防止过早解决方案？" | **反转** —— 让 Agent 在行动前进行访谈 |
| "如何强制多步执行？" | **流水线** —— 使用硬性检查点和门控条件 |

---

## 模式可以组合

这些模式不是互斥的，它们可以**组合**。

- 流水线 skill 可以在最后包含一个审查器步骤来复查自己的工作
- 生成器可以在开始时依赖反转来收集必要的变量，然后再填充模板

得益于 ADK 的 `SkillToolset` 和渐进式披露，你的 Agent 只在运行时花费上下文 token 在需要的精确模式上。

---

## 总结

不要再试图将所有复杂且脆弱的指令塞进单个系统提示词。分解你的工作流程，应用正确的结构模式，构建可靠的 Agent。
