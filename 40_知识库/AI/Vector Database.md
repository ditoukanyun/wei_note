# Vector Database
Vector Database 是向量数据库的英文入口，用于连接语义检索、RAG 和嵌入表示相关笔记。

## 相关概念
- [[向量数据库]]
- [[Embedding]]

## 工作流程

```mermaid
flowchart LR
  A[文本或图片] --> B[生成向量]
  B --> C[写入向量索引]
  C --> D[相似度检索]
  D --> E[返回候选结果]
```

## 实践检查清单

- 向量维度是否与 Embedding 模型匹配。
- metadata 是否包含来源、权限、版本和时间。
- 是否设计删除、更新和重建索引流程。
- 是否用真实查询评估召回率和延迟。
- 是否区分开发本地向量库和生产托管/集群方案。

## 案例

RAG 知识库把文档切分后写入向量数据库，用户提问时先检索相似片段，再把片段作为上下文交给模型生成答案。

## 设计边界

向量数据库解决语义相似检索，但不自动解决事实正确、权限过滤和版本治理。生产 RAG 通常还需要关键词检索、重排序、元数据过滤、引用回溯和答案评估。向量检索召回的是候选上下文，不等于最终答案。

选型时要看数据规模、更新频率、延迟目标、部署方式和权限模型。本地原型可以轻量，生产系统则要考虑备份、迁移、监控和多租户隔离。

排查召回质量时，应同时检查切块、Embedding、过滤条件、相似度指标和重排策略，不能只把问题归因于向量数据库。

## 常见误区

- 把向量数据库当关系数据库使用，忽略元数据和版本管理。
- 只看 top-k 结果数量，不评估召回质量。
- 文档更新后旧向量未删除，导致过期内容被引用。

## 复盘问题

- 检索结果是否能追溯到原文、版本、权限和切块策略。
- 召回失败时能否判断问题来自切块、Embedding、索引、过滤还是重排。
- 数据删除和更新是否同步影响向量、元数据和答案引用。
