**CLAUDE.md、自定义命令、技能、智能体与权限的完整指南，以及正确的配置方法。**

大多数 Claude Code 用户把 **.claude 文件夹**当作黑盒。他们知道它的存在，也见过它出现在项目根目录。但他们从未打开过它，更没有真正弄懂里面每个文件的作用。

这是一个被浪费的机会。

**.claude 文件夹是控制 Claude 行为方式的控制中心。** 它存放着你的指令、自定义命令、权限规则，甚至 Claude 跨会话的记忆。一旦你搞清楚各个文件的位置和用途，就能把 Claude Code 配置成完全符合团队需求的状态。

本指南将逐一拆解该文件夹的完整结构，从日常高频使用的文件，到配置一次就可以忘掉的文件。

# 两个文件夹，不是一个

在深入之前，有一点值得提前说明：实际上存在两个 .claude 目录，而不是一个。

第一个位于你的项目内部，第二个位于你的主目录（home directory）：

**项目级文件夹存放团队配置。** 你将其提交到 Git。团队中所有人都共享同一套规则、同一批自定义命令、同一套权限策略。

全局的 **~/.claude/** 文件夹存放你的个人偏好和机器本地状态，例如会话记录和自动记忆（auto-memory）。

# CLAUDE.md：Claude 的使用手册

这是整个系统中最重要的文件。启动 Claude Code 会话时，它读取的第一个文件就是 **CLAUDE.md**。该文件会被直接加载到系统提示词（system prompt，即对话开始前注入给模型的隐藏指令层）中，并在整个对话过程中持续生效。

简而言之：**你在 CLAUDE.md 中写什么，Claude 就遵照执行。**

如果你告诉 Claude 始终在实现之前先写测试，它就会这样做。如果你写明"错误处理禁止使用 console.log，必须使用自定义 logger 模块"，每次它都会遵守。

**CLAUDE.md** 放在项目根目录是最常见的做法。你也可以在 **~/.claude/CLAUDE.md** 中添加全局偏好，使其适用于所有项目，甚至可以在子目录中单独放一份，用于目录级别的规则。Claude 会读取所有这些文件并合并。

CLAUDE.md 中该写什么

大多数人要么写太多，要么写太少。以下是有效的写法。

## 应该写：

- 构建、测试和 lint 命令（如 npm run test、make build 等）
- 关键的架构决策（例如"我们使用基于 Turborepo 的单体代码仓库（monorepo）"）
- 不易察觉的注意事项（例如"TypeScript 开启了 strict 模式，未使用的变量会报错"）
- 导入约定、命名规范、错误处理风格
- 主要模块的文件和目录结构

## 不应该写：

- 应该放在 linter 或 formatter 配置中的内容
- 可以直接链接的完整文档
- 解释理论的长段落

CLAUDE.md 保持在 200 行以内。超过这个长度，文件会占用过多上下文（即上下文窗口，context window，模型一次能"记住"的文本量上限），Claude 的指令遵从度实际上会下降。

下面是一个简洁而实用的示例：

```markdown
# Project: Acme API

## Commands
npm run dev          # Start dev server
npm run test         # Run tests (Jest)
npm run lint         # ESLint + Prettier check
npm run build        # Production build

## Architecture
- Express REST API, Node 20
- PostgreSQL via Prisma ORM
- All handlers live in src/handlers/
- Shared types in src/types/

## Conventions
- Use zod for request validation in every handler
- Return shape is always { data, error }
- Never expose stack traces to the client
- Use the logger module, not console.log

## Watch out for
- Tests use a real local DB, not mocks. Run \`npm run db:test:reset\` first
- Strict TypeScript: no unused imports, ever
```

约 20 行。它给了 Claude 在这个代码库中高效工作所需的一切，无需频繁确认。

# CLAUDE.local.md：个人覆盖配置

有时你有一些只属于自己的偏好，而不是整个团队的。也许你偏好不同的测试运行器，或者希望 Claude 总是按特定模式打开文件。

在项目根目录创建 CLAUDE.local.md 即可。Claude 会同时读取主 CLAUDE.md 和它，并且该文件会被自动 Git 忽略（gitignored，即不纳入版本控制追踪），你的个人配置不会进入代码仓库。

# rules/ 文件夹：可扩展的模块化指令

CLAUDE.md 对单个项目效果很好。但随着团队规模扩大，你最终会得到一个 300 行、没人维护、所有人都忽略的 CLAUDE.md。

rules/ 文件夹解决了这个问题。

**.claude/rules/ 中的每个 Markdown 文件都会随 CLAUDE.md 自动加载。** 你无需维护一个庞大的文件，而是按关注点拆分指令：

```markdown
.claude/rules/
├── code-style.md
├── testing.md
├── api-conventions.md
└── security.md
```

每个文件保持专注，易于更新。负责 API 约定的团队成员编辑 api-conventions.md，负责测试规范的人编辑 testing.md，互不干扰，相互覆盖的问题迎刃而解。

真正的威力来自**路径限定规则（path-scoped rules）**。在规则文件中添加 YAML 前置元数据（YAML frontmatter，Markdown 文件顶部以 --- 包裹的结构化元信息）块，该规则就只会在 Claude 处理匹配路径的文件时激活：

```markdown
---
paths:
  - "src/api/**/*.ts"
  - "src/handlers/**/*.ts"
---
# API Design Rules

- All handlers return { data, error } shape
- Use zod for request body validation
- Never expose internal error details to clients
```

当 Claude 在编辑 React 组件时，该文件不会被加载。只有在处理 src/api/ 或 src/handlers/ 中的文件时才会加载。没有 paths 字段的规则则无条件加载，每次会话都生效。

当 CLAUDE.md 开始显得拥挤时，这就是正确的解决模式。

# commands/ 文件夹：自定义斜杠命令

Claude Code 内置了 **/help** 和 **/compact** 等斜杠命令（slash command，在 CLI 界面以 / 开头输入的快捷指令）。**commands/** 文件夹允许你添加自己的命令。

**在 .claude/commands/ 中放入的每个 Markdown 文件都会成为一条斜杠命令。**

名为 **review.md** 的文件创建 **/project:review**，名为 fix-issue.md 的文件创建 **/project:fix-issue**。文件名即命令名。

以下是一个简单示例。创建 **.claude/commands/review.md**：

```markdown
---
description: Review the current branch diff for issues before merging
---
## Changes to Review

!\`git diff --name-only main...HEAD\`

## Detailed Diff

!\`git diff main...HEAD\`

Review the above changes for:
1. Code quality issues
2. Security vulnerabilities
3. Missing test coverage
4. Performance concerns

Give specific, actionable feedback per file.
```

在 Claude Code 中运行 **/project:review**，它会在 Claude 看到提示词之前自动将真实的 git diff 注入进去。**!** 加反引号的语法会执行 Shell 命令并将输出嵌入。这正是这些命令真正有用而非只是保存文本的原因。

## 向命令传递参数

使用 $ARGUMENTS（接收命令名称后面传入文本的占位变量）来传递命令名称后面的文本：

```markdown
---
description: Investigate and fix a GitHub issue
argument-hint: [issue-number]
---
Look at issue #$ARGUMENTS in this repo.

!\`gh issue view $ARGUMENTS\`

Understand the bug, trace it to the root cause, fix it, and write a
test that would have caught it.
```

运行 **/project:fix-issue 234** 会将 issue 234 的内容直接注入提示词。

## 个人命令 vs 项目命令

**.claude/commands/** 中的项目命令会被提交并与团队共享。如果你想要在所有项目中都能使用的命令，放在 **~/.claude/commands/** 中，它们会显示为 **/user:command-name**。

个人命令的使用场景：每日站会助手、按你惯用格式生成提交信息的命令，或快速安全扫描。

# skills/ 文件夹：按需调用的可复用工作流

你现在了解了命令的工作方式。技能（skills）表面上与之相似，但触发方式有本质不同。在深入之前先说清楚这个区别：

**技能是 Claude 可以主动调用的工作流**，无需你输入斜杠命令，只要任务与技能描述匹配，Claude 就会自行触发。命令等待你的指令，技能则监听对话并在时机合适时自动执行。

每个技能存放在各自的子目录中，包含一个 SKILL.md 文件：

```markdown
.claude/skills/
├── security-review/
│   ├── SKILL.md
│   └── DETAILED_GUIDE.md
└── deploy/
    ├── SKILL.md
    └── templates/
        └── release-notes.md
```

SKILL.md 使用 YAML 前置元数据描述其触发条件：

```markdown
---
name: security-review
description: Comprehensive security audit. Use when reviewing code for
  vulnerabilities, before deployments, or when the user mentions security.
allowed-tools: Read, Grep, Glob
---
Analyze the codebase for security vulnerabilities:

1. SQL injection and XSS risks
2. Exposed credentials or secrets
3. Insecure configurations
4. Authentication and authorization gaps

Report findings with severity ratings and specific remediation steps.
Reference @DETAILED_GUIDE.md for our security standards.
```

当你说"检查这个 PR 是否有安全问题"时，Claude 读取描述，识别到匹配，并自动调用该技能。你也可以通过 **/security-review** 显式调用。

**与命令的关键区别**：技能可以捆绑配套文件。上面 [@DETAILED\_GUIDE](https://x.com/@DETAILED_GUIDE).md 的引用会拉取一份与 SKILL.md 并列存放的详细文档。命令是单个文件，技能是完整的包。

个人技能放在 **~/.claude/skills/** 中，跨所有项目可用。

# agents/ 文件夹：专业化的子智能体角色

当任务足够复杂、值得专人处理时，你可以在 .claude/agents/ 中定义子智能体（subagent，为处理子任务而独立启动的第二个 AI 实例）角色。每个智能体是一个 Markdown 文件，拥有独立的系统提示词、工具访问权限和模型偏好：

```markdown
.claude/agents/
├── code-reviewer.md
└── security-auditor.md
```

code-reviewer.md 的内容示例：

```markdown
---
name: code-reviewer
description: Expert code reviewer. Use PROACTIVELY when reviewing PRs,
  checking for bugs, or validating implementations before merging.
model: sonnet
tools: Read, Grep, Glob
---
You are a senior code reviewer with a focus on correctness and maintainability.

When reviewing code:
- Flag bugs, not just style issues
- Suggest specific fixes, not vague improvements
- Check for edge cases and error handling gaps
- Note performance concerns only when they matter at scale
```

当 Claude 需要完成代码审查时，它会在独立的上下文窗口中启动该智能体。智能体完成工作后，压缩结果并汇报。你的主会话不会被大量中间探索过程的 token 所污染。

tools 字段限制了智能体能做的事情。安全审计员只需要 Read、Grep 和 Glob。它没有任何理由写入文件。这个限制是有意为之的，值得明确声明。

model 字段允许你为专项任务使用更便宜、更快速的模型。Haiku 能很好地处理大多数只读探索任务。把 Sonnet 和 Opus 留给真正需要它们的工作。

个人智能体放在 **~/.claude/agents/** 中，跨所有项目可用。

# settings.json：权限与项目配置

**.claude/** 中的 **settings.json** 文件控制 Claude 被允许和禁止做的事情。在这里你可以定义 Claude 能运行哪些工具、能读取哪些文件，以及在执行某些命令前是否需要先征询意见。

完整文件示例如下：

```markdown
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Read",
      "Write",
      "Edit"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(curl *)",
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

## 各部分的作用

[$schema](https://x.com/search?q=%24schema&src=cashtag_click) **行**在 VS Code 或 Cursor 中启用自动补全和内联校验。建议始终包含此行。

**允许列表（allow list）** 包含无需 Claude 请求确认即可运行的命令。对大多数项目而言，合理的允许列表应涵盖：

- Bash(npm run \*) 或 Bash(make \*) 以便 Claude 自由运行脚本
- Bash(git \*) 用于只读 git 命令
- Read、Write、Edit、Glob、Grep 用于文件操作

**拒绝列表（deny list）** 包含被完全屏蔽的命令，无论如何都不会执行。合理的拒绝列表应屏蔽：

- 破坏性 Shell 命令，如 rm -rf
- 直接网络命令，如 curl
- 敏感文件，如 .env 及 secrets/ 中的所有文件

**如果某个命令既不在允许列表也不在拒绝列表，Claude 会在执行前先询问。** 这个中间地带是有意设计的。它提供了安全网，同时无需你预先列举所有可能的命令。

## settings.local.json：个人覆盖配置

与 **CLAUDE.local.md** 相同的思路。创建 **.claude/settings.local.json** 来添加不想提交的权限变更，该文件会被自动 Git 忽略。

# 全局 ~/.claude/ 文件夹

你不会经常与这个文件夹打交道，但了解其中的内容很有用。

**~/.claude/CLAUDE.md** 会加载到所有项目的每一次 Claude Code 会话中。这里适合存放你个人的编码原则、偏好风格，或任何你希望 Claude 记住的内容，无论在哪个代码仓库中都生效。

**~/.claude/projects/** 存储每个项目的会话记录和自动记忆。Claude Code 在工作过程中会自动向自身保存笔记：发现的命令、观察到的模式、架构洞察。这些内容跨会话持久保存，你可以通过 /memory 浏览和编辑。

**~/.claude/commands/** 和 **~/.claude/skills/** 存放跨所有项目可用的个人命令和技能。

通常不需要手动管理这些内容。但了解它们的存在很有帮助——当 Claude"记得"你从未告诉过它的事情时，或者当你想清除某个项目的自动记忆重新开始时，你就知道该去哪里找了。

## 全貌

所有内容整合在一起的结构如下：

```markdown
your-project/
├── CLAUDE.md                  # Team instructions (committed)
├── CLAUDE.local.md            # Your personal overrides (gitignored)
│
└── .claude/
    ├── settings.json          # Permissions + config (committed)
    ├── settings.local.json    # Personal permission overrides (gitignored)
    │
    ├── commands/              # Custom slash commands
    │   ├── review.md          # → /project:review
    │   ├── fix-issue.md       # → /project:fix-issue
    │   └── deploy.md          # → /project:deploy
    │
    ├── rules/                 # Modular instruction files
    │   ├── code-style.md
    │   ├── testing.md
    │   └── api-conventions.md
    │
    ├── skills/                # Auto-invoked workflows
    │   ├── security-review/
    │   │   └── SKILL.md
    │   └── deploy/
    │       └── SKILL.md
    │
    └── agents/                # Specialized subagent personas
        ├── code-reviewer.md
        └── security-auditor.md

~/.claude/
├── CLAUDE.md                  # Your global instructions
├── settings.json              # Your global settings
├── commands/                  # Your personal commands (all projects)
├── skills/                    # Your personal skills (all projects)
├── agents/                    # Your personal agents (all projects)
└── projects/                  # Session history + auto-memory
```

从零开始的实践步骤

如果你从零开始，以下是一套行之有效的渐进方式。

**第一步。** 在 Claude Code 中运行 /init。它会通过读取你的项目生成一份初始 CLAUDE.md。将其精简到核心内容。

**第二步。** 添加 .claude/settings.json，配置适合你技术栈的允许/拒绝规则。至少允许你的运行命令，并拒绝 .env 文件读取。

**第三步。** 为你最常用的工作流创建一两条命令。代码审查和问题修复是不错的起点。

**第四步。** 随着项目增长、CLAUDE.md 开始拥挤，着手将指令拆分到 .claude/rules/ 文件中。在合理的地方按路径限定范围。

**第五步。** 添加 ~/.claude/CLAUDE.md，写入你的个人偏好。可能是"始终在实现之前先定义类型"或"偏向函数式而非面向对象的写法"。

这对于 95% 的项目来说已经完全够用了。技能和智能体适合在你有值得封装的复杂重复工作流时再引入。

## 核心洞察

**.claude 文件夹**本质上是一套协议，用于告诉 Claude 你是谁、你的项目做什么、它应该遵循哪些规则。你定义得越清晰，花在纠正 Claude 上的时间就越少，它做有价值工作的时间就越多。

**CLAUDE.md 是你最高杠杆率的文件。** 首先把它做好，其他的都是优化。

从小处着手，边用边完善，把它当作项目中的任何一件基础设施来对待：一旦搭好，每天持续创造价值。

## 实践流程

```mermaid
flowchart LR
  A[运行 init] --> B[精简 CLAUDE.md]
  B --> C[配置 settings 权限]
  C --> D[沉淀 commands 和 rules]
  D --> E[按需增加 skills 和 agents]
```

## 实践检查清单

- CLAUDE.md 是否只保留高价值、稳定的项目约定。
- settings 是否明确允许命令和拒绝敏感文件。
- commands 是否覆盖高频工作流，而不是零散口令。
- rules 是否按目录或技术栈拆分，避免主文件膨胀。
- skills 和 agents 是否在真实重复任务出现后再创建。

## 案例

一个后端项目可以在 CLAUDE.md 中记录运行测试、代码风格和模块边界；把“修复 issue”“生成迁移说明”做成 commands，把安全审查做成 Skill。

## 常见误区

- CLAUDE.md 越写越长，导致缓存和注意力成本上升。
- 权限配置过宽，允许读取密钥文件。
- 没有先验证工作流，就过早创建复杂 Skill。
