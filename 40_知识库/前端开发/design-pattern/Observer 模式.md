# Observer 模式

Observer 模式让对象在状态变化时通知订阅者，常用于响应式系统、事件系统和状态管理。

## 工作流程

```mermaid
flowchart TD
    A["Subject 状态变化"] --> B["通知 Observers"]
    B --> C["Observer 执行更新逻辑"]
    C --> D["UI 或派生状态变化"]
```

## 核心角色

- Subject：被观察对象，维护订阅者列表。
- Observer：观察者，接收变化通知。
- Subscribe/Unsubscribe：注册和取消订阅。
- Notify：状态变化后触发通知。

## 实践检查清单

- 订阅和取消订阅是否成对出现。
- 通知时是否避免死循环和重复更新。
- 观察者之间是否互相强耦合。
- 异步通知是否需要调度或批处理。
- 是否有调试手段追踪谁触发了更新。

## 案例

Vue 响应式系统中，数据变化会通知依赖它的 watcher 更新；浏览器事件监听也是观察者模式的一种形式，事件源变化后通知监听器执行回调。

## 适用边界

Observer 模式适合“一处变化，多处响应”的场景。它能降低状态源和响应者之间的直接依赖，但会增加变化链路的隐式性。系统越大，越需要可观测的订阅关系、清晰的取消订阅机制和批量更新策略。

在 UI 框架中，观察者通常不会立即无脑更新，而是配合调度器合并更新，避免一次状态变化触发过多渲染。业务代码中如果使用事件总线，也要限制事件命名和作用域，否则很容易变成难追踪的全局通信。

判断实现是否健康，可以看“谁订阅了谁”能否被快速回答。若一个状态变化会触发大量隐式副作用，就需要补调试日志、事件命名规范或更明确的状态管理边界。

## 常见误区

- 只订阅不取消，造成内存泄漏。
- 通知链过长，导致变化来源难追踪。
