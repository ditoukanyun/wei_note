# gRPC
gRPC 是基于 HTTP/2 和 Protocol Buffers 的 RPC 框架，适合服务间高性能调用。

## 相关概念
- [[RESTful API 设计]]
- [[OpenAPI]]

## 调用流程

```mermaid
flowchart LR
  A[定义 proto] --> B[生成客户端和服务端代码]
  B --> C[客户端调用方法]
  C --> D[HTTP/2 传输二进制消息]
  D --> E[服务端处理并返回]
```

## 适用场景

- 内部服务间高性能、强契约调用。
- 多语言服务需要统一接口定义。
- 流式传输、双向通信或低延迟 RPC 场景。

## 实践检查清单

- proto 字段编号是否稳定，避免破坏兼容性。
- 超时、重试、熔断和负载均衡是否统一配置。
- 错误码是否映射为业务可理解的异常。
- 是否有反射、健康检查和链路追踪支持。
- 对外开放 API 是否仍需要 HTTP/JSON 网关。

## 适用边界

gRPC 更适合内部强契约服务调用，不一定适合所有外部开放接口。浏览器、网关、调试工具和合作方接入成本都要考虑。若主要使用者是 Web 前端或第三方开发者，HTTP/JSON 可能更容易调试和集成。

proto 演进要遵守兼容规则：字段编号不要复用，删除字段要保留编号，新增字段要考虑老客户端默认值。契约稳定性比单次性能收益更重要。

服务治理也不能省略。gRPC 调用同样需要超时、重试、限流、链路追踪和错误语义，否则高性能只会更快放大故障。

## 常见误区

- 频繁修改字段编号或删除字段，破坏老客户端。
- 把 gRPC 直接暴露给浏览器，忽略浏览器兼容和网关需求。
- 只关注性能，不做可观测性和错误治理。

## 复盘问题

- proto 变更是否兼容老客户端，并有版本管理策略。
- 超时、重试、负载均衡和链路追踪是否和 HTTP 服务一样完整。
