# 分支管理

## 定义

分支管理是用分支隔离不同功能、修复和发布工作的 Git 实践。好的分支策略能减少冲突、降低发布风险，并让代码评审和回滚更清晰。

## 常见流程

```mermaid
flowchart LR
    A["main"] --> B["feature/login"]
    B --> C["提交与自测"]
    C --> D["Pull Request"]
    D --> E["Code Review"]
    E --> F["合并 main"]
```

分支存在的意义是隔离变化，不是长期堆积代码。分支越久，和主分支偏离越大，冲突和集成风险越高。

## 常见策略

- **Feature Branch**：每个功能一个分支，适合常规团队协作。
- **Git Flow**：区分 develop、release、hotfix，适合发布节奏较重的团队。
- **Trunk Based**：小步高频合入主干，适合自动化测试和发布成熟的团队。

## 检查清单

- 分支命名是否表达功能、修复或实验目的。
- 是否定期同步主分支，避免大冲突。
- 分支是否足够短生命周期。
- 合并前是否经过测试和 [[Code Review]]。
- 紧急修复是否有独立 hotfix 流程和回滚方案。

## 命名示例

- `feature/order-export`：新增订单导出功能。
- `fix/login-token-expiry`：修复登录 Token 过期问题。
- `hotfix/payment-timeout`：生产支付超时紧急修复。
- `chore/update-deps`：依赖升级或维护任务。

## 常见误区

- 一个分支长期承载多个不相关功能，导致评审和回滚困难。
- 分支从旧基线切出后长期不同步主分支。
- 功能未完成就混入格式化、重命名等大规模无关改动。
- 没有保护主分支，导致未经评审的代码直接进入发布线。
